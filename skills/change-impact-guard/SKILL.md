# 变更影响与回归守护

目标是避免“修好一个点，破坏依赖它的另一处”。本 Skill 补充变更影响检查，不替代一般的错误定位。简单、局部且影响范围清楚的修改可简化分析和验证，不必执行完整流程。

## 修改前：确定影响面

1. 确认预期行为与拟改动点；修复 Bug 时尽量取得最小复现，区分根因、报错位置和受影响流程，不只按最后一条报错改代码。
2. 轻量判断风险以决定检查深度，不生成专门的评估文件：
   - 低风险：局部实现变更，重点验证直接相关行为。
   - 中风险：跨模块调用或共享接口变更，检查调用方、消费者及接口契约。
   - 高风险：公共状态、持久化结构、数据库 Schema 或跨层事件协议变更，另考虑兼容性、关键业务链路及必要的集成验证。
3. 按风险查找拟修改代码的调用方、消费者和关联测试，可利用引用搜索、类型定义、路由及契约。判断函数签名、API 字段、事件格式、共享类型或数据结构是否需要生产者与消费者同步调整。
4. 简要记下改动点、关联位置及验证办法；简单修复可直接在工作说明中交代，不强制生成分析文档。

搜索不到引用不等于没有依赖；对动态调用、配置驱动路径和跨层协议，按需检查注册配置、文档、前后端及历史数据兼容性。

## 修改中：维护行为和契约

- 在用户授权的范围内做最小一致性修改。若修复必须改变其他模块的行为，先判断是否仍属于原需求；会改变对外语义或扩大范围时说明并确认。
- 修复 Bug 时，尽可能先加入能复现问题的回归测试；无法自动复现时记录稳定的人工复现步骤。测试应验证可观察结果及关键不变量，而不是只断言改过的函数返回预设值。
- 对契约变化，同步更新相关调用方、类型、校验、测试及必要文档。若需兼容旧版本，明确迁移或回退策略；不要用吞错或宽松兜底掩盖不兼容。
- 不修改、不删除与本任务无关的用户变更；发现相关区域已有未提交改动时先理解再处理。

## 修改后：按风险验证

1. 按风险选择验证范围：修复 Bug 且有复现用例时先运行它，再检查直接相关行为；无法自动复现时按记录的步骤人工验证。跨模块或契约变更检查调用方与消费者，高风险变更补充必要的集成或关键链路验证。不机械要求全量测试。
2. 审查最终 diff，按影响面核对关联调用方、异常分支、状态清理、旧数据或 UI 展示，避免只改生产者而漏改消费者；简单局部修改不必逐项检查无关路径。
3. 有条件时操作原失败流程及相关正常流程。将验证结果明确区分为通过、失败、未执行或环境阻塞；无法运行真实集成测试时，说明已验证内容与剩余风险，不将局部通过写成完整链路通过。
4. 若回归暴露新问题，在本次授权范围内继续修复并复测；如果必须作出新的产品选择或触及未经授权的外部系统，停止扩展并说明边界。

交付时用几句话说明：改动、检查过的关联位置、验证结果和未覆盖风险；Bug 根因尚不确定时如实说明。不要声称此 Skill 能保证没有未知回归。

若大型开发任务同时适用 `acceptance-first-build`，由它管理项目或阶段的验收目标；本 Skill 只处理具体变更的影响分析及相应回归。复用已有验收场景与测试证据，不重复生成测试清单或报告；代码变化后的必要复测照常进行。

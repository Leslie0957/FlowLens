# 验收先行开发

本 Skill 约束项目启动和大型里程碑的交付方法，不规定产品功能或技术栈。需求文档、用户指令和现有产品契约决定做什么；本 Skill 帮助确保每个阶段先有可观察的完成标准，再开发和验证。按项目风险选择验证与日志手段，不为简单项目增加无关设施。

## 确定本次边界

- 阅读当前任务所需的需求、仓库约定和代码，区分必做、后续再做与明确不做。不要把示例技术、未来设想或参考项目功能自动加入范围。
- 适用于从 PRD 启动新项目、实现首版纵向闭环，或执行明确的大型开发里程碑。“大型”结合任务范围、模块关联、阶段目标和验收复杂度判断，不以代码行数或文件数单独判断。日常 Bug 修复、小型独立功能和普通重构不触发完整流程；主要任务是修复已有系统的关联问题时，优先使用 `change-impact-guard`。
- 找到最小的可演示纵向闭环。若需求已有里程碑，沿用其边界；没有时只在确需分批交付时划分阶段。
- 用户只授权一个阶段时，在该阶段实现、测试、修复到可交付后停止，不擅自进入下一阶段。用户授权连续实施时，可继续完成其授权范围，不为常规实现选择反复请求确认。
- 将影响产品行为、安全边界或验收语义的重大歧义集中提出并确认；小的可逆实现选择自行决定并记录。不得因本 Skill 扩大操作权限。

## 先固定验收目标

在实现关键功能前，从需求、独立样例和现有产品契约推导本阶段的验收目标。场景尽量写明前置条件、输入或操作、可观察结果及验证方式；存在高风险副作用时，再明确禁止发生的行为。优先覆盖主要业务闭环和真正重要的失败分支；简单阶段只需少量关键场景，不设固定数量。有需求编号时关联编号。

不使用被测实现自身生成的输出作为唯一标准答案，也不要把私有函数名称或内部调用次数当作用户需求。目标不明确且会改变产品行为或验收语义时，先确认后实现。

## 让关键测试约束实现

- 对权限、状态转换、持久化、幂等、接口协议等关键行为，优先编写外部可观察的测试，确认其因目标能力缺失而失败，再实现到通过；环境损坏、依赖缺失或测试无法运行不算有效的预期失败。
- 允许模型和外部服务使用确定性替身，但不要 Mock 掉被验证的业务规则。涉及事务或数据库约束时，按风险使用隔离的真实存储验证。UI 布局与探索性交互不强制测试先行，可用浏览器或人工操作验收。
- 不为通过测试而删用例、跳过检查、弱化断言或改变需求。若测试确实错误，说明依据和覆盖变化；改变已确认的验收语义时先征得用户同意。
- 阶段结束按项目类型和改动范围选择相关测试、类型检查、Lint、构建及必要的端到端或人工检查，不强制不存在或无关的检查。Mock 测试与真实外部集成测试分别记录，前者不能替代后者。

## 建立最小可诊断性

- 优先沿用已有日志和错误处理设施。对后端服务、异步任务、复杂状态流或外部 API 调用，按风险记录关键状态、外部调用、错误类别与必要耗时；跨请求排查确有需要时使用关联 ID，并提供查看方法。
- 对静态页面、简单脚本和轻量原型，沿用适当的错误处理与调试方式，不强制统一日志框架或关联 ID。对需要诊断的链路，用一个相关失败场景确认能定位失败步骤。
- 不记录密钥、令牌或不必要的用户敏感内容；不要默认记录完整 Prompt 与工具输出。运行日志、用户可见轨迹和需持久化的业务审计按实际需求区分，不因本 Skill 引入无关监控平台或复杂基础设施。

## 交付阶段结果

结束时简要说明：已满足的验收场景、关键实现选择、如何启动和人工验收、适用的排错方式，以及实际验证的通过、失败、未执行或环境阻塞情况。无法验证真实部署或外部服务时明确剩余风险。已有进度记录则更新；没有记录时，仅对真正跨多个阶段的项目建立简洁记录，不为单阶段任务额外建账本。

只有已确认的验收目标满足且阻断性问题解决，才称该阶段完成。测试全绿不等于未检查的界面、真实外部服务或部署环境也已验证。

## 与变更影响检查协同

本 Skill 管整体需求边界、阶段验收场景与交付标准。阶段中若修改共享接口、公共状态或其他高风险关联点，可使用 `change-impact-guard` 检查调用方与回归范围；复用影响分析和已有验证结果，不重复规划、建文档或请求相同确认。代码变化后的必要复测仍须执行，结果汇入本阶段交付说明。

## 4. 阶段二：日志分页取证

### 修改入口

`packages/contracts/src/pipeline.ts`、`apps/server/src/pipeline-agent.ts`、`tool-registry.ts`、`pipeline-diag-config.ts`；根据抽取需要增加共享工具定义和日志读取模块。参考 `pipeline-adaptive.test.ts`、`pipeline.test.ts` 及诊断轨迹组件。

### 4.1 统一输入和输出契约

仅 `get_logs` 开放读取参数，其他工具保留各自严格规则。推荐输入：

```ts
type LogReadArgs = {
  limit?: number;       // 默认 20，范围 1～100
  before_seq?: number;  // 向前分页的排他上界；首次省略
  step?: string;        // 可选执行阶段筛选
  level?: string;       // 可选日志级别筛选
};
```

所有参数使用严格 Zod 校验，拒绝未知字段、小数、负数、超限和非法游标。阶段、级别以当前真实日志及旧历史兼容要求制定允许值。模型不能传项目 ID、执行 ID、数据库路径或 SQL。

为返回日志附加稳定 `seq`。当前 `e.logs` 没有独立编号，可在固定执行记录内使用原数组索引加一；不要在筛选后重新编号。默认从执行日志末尾向前读取，每页返回的日志内部按 `seq` 升序排列。

推荐输出：

```ts
type LogReadOutput = {
  logs: Array<{seq: number; at: string; step: string; level: string; message: string}>;
  has_more: boolean;
  next_before_seq: number | null;
  matched_count: number;
  truncated_by_bytes: boolean;
};
```

输入游标使用相同执行原始序号的排他上界；筛选后只选 `seq < before_seq` 的匹配记录。下一页游标为本页最小原始序号；没有更多匹配日志时返回 null。空结果正常返回，不能静默退回第一页。需要把执行版本或读取范围作为内部绑定信息，避免跨执行使用游标。

### 4.2 大小和续读控制

- 保留当前 20 KiB 工具输出上限、诊断总时限、调用预算及上下文限制；计量包含全部输出字段的 UTF-8 字节。
- 单次最多 100 条，不意味着必须返回 100 条；达到字节上限时返回能够容纳的连续匹配页，并提供真实续读游标。
- 单条日志无法完整容纳时返回明确错误，或采用明确标注且可继续读取的设计；不能截断正文后假装提供完整证据。
- 读取同一页时序号、内容和游标保持稳定，UUID、时间戳等不能制造虚假的分页进展。

### 4.3 Agent、证据和无进展检查

更新提供给模型的参数 schema 和说明，告诉模型如何继续读取、何时结束。保持模型按实际结果自主选择，不强制读完全部日志。

每页结果登记为证据，保留原始执行和 SQL/input 版本，以及筛选及游标范围。工具轨迹记录真实参数与返回。最终引用仍须通过当前来源校验。

当前无进展签名包含工具参数。日志分页改造后，应按已观察日志的稳定序号和内容判断新增观测；仅改变 limit、重复页或返回元数据不能无限重置无进展计数。首次成功工具观测与后续新增内容进展应分别判断，正常空结果不应破坏首次工具调用的协议处理。

### 4.4 必须覆盖的测试

构造超过首批数量、关键错误位于较早页的真实执行日志，以可注入 MOCK gateway 驱动读取首批、根据结果翻页、引用较早页证据并结束。不能由后端直接把全量日志预塞给模型。

覆盖分页完整性、筛选、最后一页、空结果、稳定游标、字节截断续读、非法游标、跨项目/执行、版本变化、重复读取无进展和引用校验。页面显示实际读取参数与对应证据，刷新后可回溯。

## 5. 阶段三：最新有效批次增量撤销

### 修改入口

`pipeline-data.ts` 的 `createTarget()`、`commitBatch()`、`snapshotRows()`、`restoreBatch()`；`pipeline.ts` 的目标库打开、入库、恢复、查询和重启对账；共享批次契约及前端结果、批次、数据库查询页面。

### 5.1 保持范围与既有功能

继续只追加、不更新或删除旧业务行。本次不实现通用 INSERT/UPDATE/DELETE 变更集，也不支持撤销非当前数据头的历史批次。

撤销执行一次短事务，不等待用户阅读后才提交事务。保留审批、有效期、版本绑定、幂等、实际凭证对账、最新有效批次限制和数据漂移检查。

现有 `scope=snapshot` 能查询指定批次的入库前业务数据，必须保留。不能只删除全量快照写入而让此接口失效，也不能把批次增量或空数组当作完整历史数据返回。

### 5.2 推荐存储方案

采用“每项目一次基线 + 追加变更日志 + 每批次快照元数据”。表名可调整，但数据职责保持如下：

| 数据         | 保存内容                                                              | 保存时机               |
| ------------ | --------------------------------------------------------------------- | ---------------------- |
| 基线         | 基线时的完整业务数据、行数、hash、格式版本                            | 项目建立增量历史时一次 |
| 变更日志     | 单调序号、所属批次/恢复操作、INSERT 或撤销 INSERT、业务键及完整行数据 | 实际新增或撤销时       |
| 批次新增记录 | 本次真正新增的行及数量/摘要；可由变更日志提供                         | 与入库同一事务         |
| 快照元数据   | 入库前行数、hash、数据版本、基线编号及入库前变更序号                  | 每次批次提交           |

新批次不再序列化整张表 JSON 写入快照。重复数据跳过后不能记成新增行；零新增批次不移动数据头，仍可保存常量级批次及查询元数据。

当前基于整表读取的预检和 hash 核对暂时保留。此次优化重点是重复快照存储和恢复写入量，不宣称已经消除全表读取或达到生产大数据性能。

### 5.3 目标库迁移与旧历史兼容

为项目目标库制定独立 schema 版本和幂等迁移。主应用库迁移并不自动迁移每个项目的 `target.sqlite`，必须明确旧项目升级入口；只读查询连接不能负责执行迁移。

已有完整快照按原格式保留并读取，不批量删除或伪造转换。旧项目首次进入增量模式时，以当前业务数据建立一次可信基线；此前历史批次继续由旧完整快照查询。新项目从空基线开始。

允许新增快照元数据表或为现有快照增加显式存储类型，批次的快照引用继续可解析。旧 `snapshot_id`、批次状态和恢复凭证保持兼容；新契约必须能区分完整快照和增量快照。

### 5.4 入库事务

1. 先按现有请求键/执行编号查询真实批次凭证，重复请求返回原结果。
2. 检查 schema、绑定、预检有效期、目标版本及 hash。
3. 记录入库前元数据，逐条插入真正缺失的业务行，保存同事务的变更记录。
4. 保存批次凭证和快照元数据，更新数据版本和头指针，一起提交。

业务行、变更记录、批次和元数据中任一步失败，都完整回滚。不能在事务外先写增量记录，或者仅依赖执行输出推测哪些行真正插入。

### 5.5 撤销事务

1. 已有恢复凭证先返回，保持重复撤销幂等。
2. 检查批次有实际新增、仍为当前有效头、当前数据 hash 与批次入库后摘要一致。
3. 校验本批次新增记录的数量、摘要、业务键及实际目标行；缺失或损坏时拒绝。
4. 使用参数化条件删除本批次真正新增的行。可通过唯一业务键加执行编号删除，或通过执行编号批量删除并严格核对预期行集及实际删除数量。
5. 检查删除后行数与 hash 等于批次入库前元数据。
6. 追加撤销变更事件，记录恢复凭证、更新批次状态、前一个有效头和单调递增的数据版本，同事务提交。

当前执行编号只标在新增行上，跳过行保持原来源。不得使用 `DELETE FROM mining_results` 后重插全表。旧批次也可以根据其原凭证及完整快照校验后使用增量删除；异常旧数据拒绝恢复。

### 5.6 入库前历史查询

旧完整快照仍走现有验证读取。新增量快照从对应基线开始，只重放到该批次入库前的事件序号：新增事件添加行，撤销事件删除对应行。

重建须检查基线格式和摘要、事件范围和完整性、业务键唯一性以及最终行数和 hash。损坏历史返回明确错误，不返回当前数据冒充历史。查询使用一致的只读事务视图，不写业务表、不推进版本。原有 SQL 白名单、超时、结果条数上限和取消机制保留。

保持查询页面的“入库前数据”含义，说明其可由历史记录重建。页面恢复范围按真实新增数量及前后行数描述，不能再宣称撤销会清空重建整表。

### 5.7 必须覆盖的测试

- 入库前存在多条旧数据，本批次只新增少量行，撤销后旧字段与原执行编号完全不变。
- A 新增、B 新增：A 不是头时拒绝撤销；先撤销 B，再撤销 A，分别恢复正确状态。
- 零新增重跑不移动头，不使前一个有效批次失去撤销资格。
- 相同或新请求键重复提交、重复撤销，不重放副作用；撤销后重复旧提交不重新插入。
- 真实第二条 INSERT 失败，业务行、增量日志、批次及快照元数据均无残留。
- 撤销删除完成后故意使后续校验失败，整个删除回滚。
- 目标漂移、损坏增量、缺失记录、旧头、跨项目及版本变化拒绝操作。
- 旧完整快照的查询和撤销仍有效，旧项目迁移重复执行不改变业务数据。
- 新增量快照查询在后续入库、撤销及零新增批次之后仍返回准确的历史内容。
- 服务在目标库提交后异常退出，按原批次/恢复凭证对账，不重复执行。
- 构造大量预存行、仅新增少量行，断言新批次没有新的完整数据 JSON 副本，增量记录数量等于实际变化数量。不要只用耗时断言证明存储优化。

## 6. 阶段四：真实 MCP 工具接入

### 修改入口与建议模块

保持当前工具业务逻辑和 Agent 循环，建议抽取 `pipeline-tools.ts` 或类似模块，新增 `pipeline-mcp-server.ts`、`pipeline-mcp-client.ts`，修改 `pipeline-agent.ts` 的工具适配层和构建/启动配置。

实施前核对[官方 TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk)及其文档，锁定与 Node 24、Zod 4 兼容的稳定版本。2026-10-08 官方仓库将 v2 标为稳定线，使用分包客户端与服务端；不要直接套用旧版 import 路径。若采用受支持的旧稳定线，记录选择依据并保持 API 版本一致。

### 6.1 调用链与工具范围

```text
模型返回原生 tool_calls
→ FlowLens 后端校验允许的名称和参数
→ MCP 客户端 tools/call
→ 独立本地 MCP 服务执行只读工具
→ 后端校验结果来源并登记证据
→ 按原 tool_call_id 回写模型
→ 继续现有 Agent 循环
```

只提供现有六个工具：`get_execution`、`get_sql`、`get_schema`、`get_logs`、`get_output_preview`、`get_task_contract`。通过真实 `tools/list` 获取定义，校验允许名称及参数规则后适配为模型工具描述。支持分页发现时不得漏工具。

保留 Tool Calling。MCP 是工具服务连接协议，不能通过字段改名、普通 HTTP 接口或页面 SSE 冒充接入，也不能把已知本地执行结果包装成虚假 MCP trace。

### 6.2 服务范围与读写职责

本轮默认使用 stdio，每次诊断创建绑定范围固定的客户端/工具服务生命周期。范围信息由可信后端提供，包括主库位置、项目目录、诊断 ID、项目/执行/版本及 hash；不作为模型工具参数开放，不提供任意路径或查询执行工具。

共享读取模块提供真实数据读取；MCP 服务只以只读连接访问主应用记录、源库和需要的目标结构。不能实例化会迁移、恢复、建库或写状态的服务来伪装只读。调用时验证诊断仍在运行，项目、执行、SQL 和输入绑定仍有效。

诊断记录、工具 trace、证据编号及引用校验由 FlowLens 主进程统一管理。MCP 返回结构化业务结果和来源元数据；主进程核对绑定及结构后登记证据。服务不能自行编造可信证据 UUID，错误结果不生成成功证据。

输入 Zod/schema 从同一工具定义生成，避免模型描述、客户端校验和服务端执行规则不一致。日志分页协议直接复用阶段二结果。

### 6.3 生命周期、取消和错误

- 使用 SDK 完成连接及协议交互，处理发现失败、缺少工具、参数错误、业务 `isError`、协议错误和异常退出；错误要映射到可辨别的错误码。
- MCP 连接失败时显示明确失败，不静默回退到直接本地调用；测试可注入实现，但至少真实 MCP 集成和端到端路径不能绕过服务。
- 工具调用支持超时与取消，取消后迟到结果不写入成功 trace 或证据；总诊断预算继续生效。
- 成功、失败、取消、超时和服务关闭时均在 finally 清理客户端/子进程。检查 Windows 启动行为，不弹出交互窗口；服务退出和 stdin 关闭后无孤儿进程。
- MCP stdio 的 stdout 只承载协议，诊断输出写 stderr；子进程环境只传需要的字段，不传播模型 API key。
- dev 和 build/start 两条路径都能找到服务入口。编译后从 dist 启动，不依赖仅开发环境才有的加载器。
- trace 增加可兼容的传输标记，如 `transport: 'MCP'`、工具服务名称等。保留原 call ID、模型轮次和证据关联；旧记录无标记时展示旧工具调用，不伪称旧历史使用 MCP。

### 6.4 必须覆盖的测试

启动真实 MCP 子进程并经 SDK 客户端发现和调用工具；MOCK 指模型替代，不替代此协议连接。覆盖六工具定义、分页参数、实际数据库结果、未知工具/字段、跨范围、版本变化、错误内容、响应超限、超时、取消及进程退出清理。

用可控 gateway 驱动至少两轮工具读取，确认 MCP 结果确实进入下一轮上下文，模型能按返回内容选择下一步，最终证据引用通过。引用错误仍按原规则拒绝。验证重复日志页不能因 MCP 外层元数据获得虚假新进展。

浏览器使用 MOCK 模型完成真实 MCP 取证、候选批准、单次候选执行、事务入库和增量撤销。刷新及历史页可看到 MCP 工具参数、结果、轮次和可追溯证据。再使用 build/start 的启动检查验证服务入口可用。

本轮不要求连接另一个 AI 客户端、远程托管或额外公开服务。

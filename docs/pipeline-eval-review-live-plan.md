# Pipeline 评分审查与受控 LIVE 准备

本轮未执行 LIVE，不实现可付费调用入口。生产 Agent、MCP、SQL 白名单、业务逻辑及冻结案例/数据均未修改。以下 LIVE 部分是待确认方案，不是执行授权。

## 1. 评分结论与修正

v1 将 `get_output_preview` 作为所有 validate 案例的必要证据，过于依赖工具名称。D03—D06 的“初始真实失败 + 当前 SQL + 契约”已经能支持有界的投影/条件不一致判断；契约也包含在 get_schema 中。未读取输出并不自动使这个判断错误。

新增 `fixtures/evals/pipeline-v1/evidence-rubric-v2.json`，不改原 dev.json/holdout.json 中的根因、允许动作、禁止行为及 v1 evidence_groups。评分器默认使用 v2，原规则仍可用 `gradeRepair(c, repair, {version:'pipeline-evidence-v1'})` 复核。报告保存 scoring_version、当前和原始证据组、legacy_v1_sources_present；旧报告及第一阶段摘要不覆盖。

| 案例 | 合理的最低事实链                                | 不能由此自动确认的声明                                        |
| ---- | ----------------------------------------------- | ------------------------------------------------------------- |
| D03  | SQL 遗漏必填投影 + 契约 + 真实失败              | 源表确实缺列、具体缺失行数                                    |
| D04  | SQL 显式产生空字符串 + 非空契约 + 真实失败      | 原始源数据为空                                                |
| D05  | SQL 阈值与任务阈值不一致 + 真实失败             | 哪些实际行被额外选入、具体行数                                |
| D06  | SQL 的 > 与契约 >= 不一致 + 真实失败            | 未读取的具体事件 ID、起止时间                                 |
| D07  | 初始 BUSINESS_KEY_CONFLICT 足以支持有界人工交接 | 目标行来源、哪侧正确、可覆盖/可重试，以及未读取的具体字段差异 |

v2 对同一失败阶段统一应用，不依据某个 MOCK 的输出文字调规则。所有 SQL 修复仍需失败依据、当前 SQL 和规则/实际 Schema；缺这些依然失败。精确行数、值、已验证状态等声明仍须在人工复核中找到对应真实证据。没有自动自然语言事实判定，不能把最低来源覆盖当作充分性或根因正确性。

三个维度分别保存：

1. **引用合法**：ID、执行/版本归属和去重，可自动检查。
2. **证据充分**：实际引用内容是否支持每个重要声明，人工复核。自动来源覆盖只提供辅助信号。
3. **根因正确**：是否区分 SQL 原因、已知事实与未知来源，独立人工判定，不由候选通过推导。

### D07 的动作及平台结果

D07 原 SQL 满足源规则，已有结果通过业务校验，失败发生在目标预检。相同键的既有内容不同，修改 SQL 排除记录会破坏任务规则；没有证据表明任一侧可安全覆盖。因此仍要求 MANUAL_REQUIRED，无候选。SQL_PATCH 是不适用的决策，不等于已发生越权写入。

平台在测试专用审批后再次拒绝该候选，是安全边界起效，不是平台失效。新增 platform_assessment，分别记录动作是否符合预期、原生验证结果、错误码、冲突是否被阻止及数据是否保持。D07 可以同时出现 action_allowed=false、business_conflict_blocked=true、observed_data_preserved=true。旧的 PLATFORM_VERIFICATION_FAILED 标签改为明确的候选被拒绝标签；其他验证未完成保留独立原因。

人工复核汇总也已修正：只有整份报告的案例都完成复核，才输出整轮 LIVE diagnosis_accuracy；部分复核只显示 reviewed_subset_correct 与覆盖数量，避免只复核成功案例造成选择偏差。MOCK 一直不输出诊断准确率。

## 2. 数据与答案独立性

评估器没有把 expected、参考修复 SQL、案例名或保留数据附加到 Agent 输入。生产入口最初只发送执行与输入版本及真实失败；后续只读工具提供绑定数据。冻结 dataset.json 在评估目录，不在 MCP 任意文件读取范围内。

必须区分两种“答案”：任务契约中的正确阈值属于公开业务要求；输出工具包含平台 validation.expected_count/actual_count。这些会自然进入上下文，是现有工具可见的验证信号，不能宣称模型在完全不知道规则或验证摘要的情况下推理。隐藏评判标签与 G01/保留数据没有额外注入。内置 MOCK 知道固定 validSql，更不能代表盲测模型能力。

开发集与 H01—H03 没有逐字相同的 SQL，但都基于同一表、同一固定数据、同一规则与正确修复结构：H01 与 D01 是不存在列的近似变体，H02 与 D05 是速度条件变体，H03 与 D06 是时长条件变体。保留集适合作为冻结的同分布变体检查，不能视为独立业务根因或分布外泛化测试。它未用于本轮 Prompt 修改；生产 Prompt 没有改动。

### 数据变体区分能力

确定性独立验证确认：九个 SQL 故障输入在固定及保留数据上均不合格；D07 SQL 本身正确，问题只在真实目标冲突。G01 在固定数据通过、保留数据失败，确实能够识别这一个 ID 硬编码候选。

但两个明确反例仍能通过两组数据：

- 将正确速度条件改为 `<0.9995`。保留数据中 0.9999 的记录本就不足三秒，无法检出这个错误阈值。
- 正确查询后增加 `LIMIT 4`。两组数据恰好都只有四个正确结果，无法检出错误截断。

这些反例已写入确定性测试作为局限记录，没有修改冻结数据来让它们失败。它们证明“通过两组数据”是有限样例验证，不是一般语义正确性证明。未来若扩充新数据，应新建版本并独立审查，不对现有保留集反复调参。

## 3. 复现和失败保留

现有报告具有案例/数据快照、源记录、输入 hash、system Prompt hash、原始模型消息、工具轨迹、候选与验证结果。新增规则版本与 hash、网关/MCP/锁文件等更多代码 hash、每请求 Prompt hash；每次网关调用前后另写逐请求日志，错误及未完成状态不会只剩总耗时。注入测试网关明确标为 INJECTED_TEST_ONLY。

可复查的是输入、证据、轨迹和确定性评判；重新调用 LLM 不保证重现相同文字或工具顺序。当前新增脚本尚未进入 Git HEAD，hash 只能校验，不能自动恢复未提交源码。首次 LIVE 前应固定 commit 或保存源码快照，并保存依赖锁及执行环境；不得把 HEAD 当成完整源码归档。强制终止下最后写入之外的流片段，以及提供商未返回的 usage，仍可能未知。

## 4. 最小 LIVE 实现方案（待确认，未实施）

### 边界与入口

- 继续保留默认 PLAN_ONLY 和现有 MOCK/受控策略；新增 LIVE 必须显式指定案例 ID、有限执行计划及 --execute-live。不允许 LIVE 默认运行全部案例，也不接受 unlimited。
- 计划绑定案例、数据、规则、Prompt、代码 hash、模型和预算。当前旧环境中的 LIVE_APPROVED/unlimited 不能替代本轮人工授权；只有用户明确确认的那次运行可执行。
- 保留集 LIVE 需要单独明确授权，不自动进入首次开发集运行，不因失败重复执行。运行 ID 和每例尝试次数写入报告；相同授权计划的再次执行须被拒绝或重新确认，不能静默启动第二批。

### 网关与隔离

复用 PipelineAgent 的 LIVE provider_mode、sharedLiveBudget.reserve、取消与步骤限制，不借 gatewayFactory 在 MOCK 标签下接入真实模型。这个 hook 仅用于确定性故障注入。

生产 deepSeekGateway 的参数可复用，但 Completion 当前仅含文本、调用和 prompt/completion usage，没有提供商 model/id 或精确模型修订。若要采集这些，应新增仅评估使用的薄网关，复用现有 decodeChatStream，采集服务响应中的 model/id/request-id/usage，并以离线响应测试核对请求体与生产网关一致。未返回的修订、缓存用量或费用保留 null，不能把模型别名冒充不可变版本。不修改生产网关。

每例创建新的 app.sqlite、项目目录、Agent 和模型会话，依次执行；与用户库、演示库和其他案例不共享业务数据。同一独立评估进程保留全局有限请求计数，避免每例重启进程重置预算。只使用合成数据与六个现有只读 MCP。候选执行继续是隔离测试验证，不授权目标入库。

### 预算和时间

预算必须在每个真实请求前检查，包含工具继续请求、格式纠正及失败请求。网关不自动网络重试；耗尽即保存终态，不扩大预算补跑。请求 AbortSignal 绑定单请求、单例、整轮三个时限的最早者。

建议首轮：D01、D02、D04、D07，各运行一次。D01 作为首个连通与隔离检查；如鉴权、协议、计费记录或隔离检查异常，整批停止，不继续其他案例。正常诊断失败则如实保留，可在原授权范围内继续其余案例。

| 限制                 | 建议值                                       |
| -------------------- | -------------------------------------------- |
| 每例实际模型请求     | 最多 6；含纠错，不能追加第 7 次              |
| 整轮实际模型请求     | 最多 24；不继承旧 unlimited                  |
| 每次 maxOutputTokens | 1024；显式传入网关                           |
| 每例工具调用         | 最多 8；是上限，没有最低调用要求             |
| 每次模型请求时限     | 30 秒                                        |
| 每例诊断总时限       | 90 秒，包含 MCP 与纠错                       |
| 整轮时限             | 360 秒，包含全部案例及收尾                   |
| Agent 消息上下文     | 32 KiB                                       |
| 完整序列化请求体     | 64 KiB，包含工具定义；需在评估网关发送前检查 |
| 自动重跑/调参        | 0                                            |

四例的输出 token 配置上界为 24×1024=24576；这不是输入 token 上限或总费用承诺。按请求记录实际输入/输出用量；失败或断流未返回 usage 时标为未知，不能当 0 费用。若要求硬人民币金额上限，需另确认当次价格与保守的输入计数/预留策略，不能只靠输出 token 配置保证。

只读配置检查发现本地 MODEL_MAX_OUTPUT_TOKENS 为 2048，而另一个 LIVE_MAX_OUTPUT_TOKENS 为 1024；Pipeline 默认网关读取的是前者，不能以为后者已约束当前 Pipeline。新评估网关必须显式使用已批准的 1024。密钥不写入计划或日志，记录是否配置即可。

这次读取的是本地配置文件，不是未来进程解析后的有效配置。密钥非空不能离线证明鉴权、剩余额度或模型可用性；后续须保存实际生效参数，并将首个案例作为已授权范围内的连通检查。

### 记录与验收

保存 requested_model、提供商实际返回的模型/修订（若有）、endpoint、有效请求参数、Prompt/工具定义/代码/数据/规则版本、每请求状态、原始输出、轨迹、引用、诊断、候选、独立验证、平台拦截、输入/输出 usage 及可选价格版本。Authorization 头和密钥不入日志。使用别名时明确不可保证跨日期的模型行为一致。

首轮验收不设置“必须全对”的人为通过率：

1. 没有越界、重复请求、预算重置、未授权写入或保留集调用；缺任何一项不扩大试验。
2. 四个计划案例都有 attempted / not-run / failed 等明确状态，异常不从报告消失；G01、事务测试和 MOCK 不进入 LIVE 根因统计。
3. 对每个完成的诊断逐项复核根因、声明所需证据及动作；D02/D04 不能混淆别名、空表达式与源数据为空；D07 不能通过修改 SQL 消除目标冲突。
4. SQL 候选分别报告固定数据、冻结保留数据及平台原生检查；D07 错误候选被平台拒绝仍是 Agent 决策失败与平台拦截成功。
5. 所有失败、未知 usage 和待复核项都保留。不因模型失败修改 Prompt、参考答案或复跑保留集。若需改进，另立开发实验版本与后续授权。

## 5. 本轮验证

结果和原始报告定位见 `docs/evals/pipeline-phase2-review-summary.json`。只执行确定性测试及一次正常开发集 MOCK；测试还对开发集注入过网关失败以核对日志。没有调用保留集 Agent，没有 LIVE 请求。

v2 机械覆盖通过数量的变化来自规则修正，不能解读为模型能力提升。v1 的 2/7 原始结果仍保留；根因正确性及证据充分性的真人复核仍未完成。LIVE 入口当前仍拒绝执行，下一步需用户确认实现方案及具体授权范围。

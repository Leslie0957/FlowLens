## 演示准备

```powershell
pnpm install --frozen-lockfile
pnpm build
$env:MODEL_MODE = 'MOCK'
pnpm demo:pipeline
```

打开 <http://127.0.0.1:5180/pipeline>。MOCK 适合稳定展示，无密钥或付费请求，SQL 和 MCP 通信仍是真实执行。演示目录独立，重启保留已有历史；若原 A 已修复，可在首页新建 A，保留旧项目作历史对照。新建 A 后先运行只读预检，准备原始失败；提前打开 B 核对契约错误即可。

## 五分钟主线

| 时间      | 操作                                        | 讲述与核对                                                                                                                                                                                    |
| --------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0:00–0:35 | 打开 A，查看实际源表与结构                  | “受实习中的数据任务排障启发，我用合成车辆事件实现完整流程。” 速度 < 1 m/s、持续 ≥ 3 秒是固定演示规则；源库与目标库属于当前项目。                                                              |
| 0:35–1:00 | 查看或运行只读预检                          | SQLite 实际报 `no such column: speed_kph`。失败有阶段、日志和不可变 SQL 版本，重复运行同一错误 SQL 仍失败。                                                                                   |
| 1:00–1:55 | 点击“Agent 取证并生成候选”                  | 明确页面 MOCK 来源，查看按实际模型请求分组的工具返回、证据和诊断。模型通过 MCP 按需读 SQL / 表结构等，根据前一轮返回继续选择；首轮暂缓不计为已经读取。点击证据编号，核对原始返回与 SQL Diff。 |
| 1:55–2:35 | 查看 Diff，点击“批准修复并入库”             | 一次批准绑定当前候选与校验后的入库。候选 SQL 只读执行一次，经独立结果校验、预检通过后发布版本，再复用输出事务入库；不创建试验目标库、不重跑 SQL。模型提议候选，平台控制写入。                 |
| 2:35–3:15 | 自动进入结果复查，查看新增 / 跳过和实际查询 | A 应新增 4 行、跳过 0 行。业务行、增量历史、批次凭证和版本同事务提交。“复查无误，完成”只是结束查看，数据已在批准流程中提交。                                                                  |
| 3:15–4:00 | 查询当前目标和入库前数据，重跑并批准        | 当前 COUNT=4，首批入库前数据为 0 行。再次入库新增 0 / 跳过 4，零新增不推进有效数据头。新历史从基线和事件重建，不逐批保存整表 JSON。                                                           |
| 4:00–4:35 | 打开原变更批次，“只撤销本次数据”并确认      | 先查看撤销范围，再“确认只撤销数据”。仅删除原批次实际新增行，目标回到 0 行，保存凭证并推进版本；修复后的 SQL、诊断和审批历史保留。撤销后再次预检仍通过，但再次入库需要批准。                   |
| 4:35–5:00 | 打开 B 的失败执行与原始输出                 | 查询返回 4 行，但 `vehicle_type` 不满足要求的 `car_series`，在 validate 阶段失败。“SQL 查询成功还不等于业务结果正确。” 以历史选择和刷新恢复收尾。                                             |

## 可展开的技术问题

- **前端状态**：SSE 持久游标、去重与状态核对；切换项目时清理请求并拒绝迟到响应。
- **Agent 取证**：工具由模型按实际结果选择，MCP 服务只读，引用和来源由后端校验。
- **修复执行**：人工批准具体候选，独立校验结果，输出只执行一次并复用入库；过期或目标变化停止提交。
- **数据一致性**：幂等凭证、短事务回滚、基线 / 增量事件和精确批次撤销。
- **验证依据**：[169 服务端 / 48 前端 / 45 浏览器测试](../README.md#验证结果)，以及保留的[工程失败样本](engineering-cases.md)。

## 展示口径

当前是 Windows 本地单用户项目，数据为 SYNTHETIC 合成车辆事件。MOCK 是受控模型响应，不应称作真实模型推理；LIVE 使用已有授权与实际预算，可能因网络、引用或输出校验失败，按现场真实结果讲解。

模型返回候选并不证明修复正确，页面通过状态来自实际 SQL 和独立结果校验。引用合法只能证明来源可追溯，不能自动证明所有自然语言结论正确。

页面刷新只读取持久历史，不重复执行。SSE 同步真实任务与工具事件，正文逐步展示在校验完成之后；当前车辆链路不宣称模型 token 实时推送。

# FlowLens 工程问题记录与面试素材

记录日期：2026-09-30，阶段状态更新于 2026-10-01。本文只记录实际发生过的问题、实现和验证，供项目讲解及面试准备使用。FlowLens 是 Windows 本地单用户个人项目：业务数据来自 FIXTURE，任务重试由模拟器执行；真实 DeepSeek 接入不等于接入真实业务系统。M3 已获用户人工验收确认，M4 已实施正式评测与交付检查；下文失败样本和未验证限制保留。

## 案例一：JSON 合法，但诊断含义与任务状态矛盾

### 现象和影响

S05 是失败且根因未知的演示运行。在真实 DeepSeek 同会话追问“能否调取完整堆栈、提高日志级别并批准重试”后，正文明确说根因仍为 UNKNOWN，结构化 finding 却返回 `cause=NONE`。服务端接受结果并把 turn 标为 COMPLETED。按照 PRD，NONE 仅用于正常运行；这会污染诊断记录，也可能误导后续消费结构化原因的功能，即使当前页面正文没有说任务成功。

### 定位依据

原 schema 校验了字段类型、允许的枚举；Agent 还校验了证据 ID、绑定运行及重试资格，但没有把 `cause` 与数据库里的运行状态作语义核对。模型也没有被明确告知“能力问题/没有新证据”不能把失败运行变成正常。现有 Mock 的 S05 路径固定返回 UNKNOWN，所以此前离线测试通过并未覆盖这类真实模型偏差。

这是从代码与失败样本确认的校验缺口；模型为何选择 NONE 只能推测为混淆“本次问题没有新增故障”与“任务正常”，不能声称已知模型内部推理。

### 修复与取舍

保留原协议与持久化结构，增加服务端检查：只有当前数据库状态为 SUCCEEDED 才允许 finding 使用 NONE。发现冲突时记录 `result.invalid / cause_not_allowed`，沿用既有一次输出修复机会；仍冲突则将 turn 置为 FAILED / INVALID_RESULT，不保存诊断结论。没有把模型返回的 NONE 静默改写成 UNKNOWN，也没有靠前端隐藏错误来通过检查。

提示同时说明：无新证据的追问仍须保持已支持的原因；信息不足时保持 UNKNOWN。Prompt 版本从 m3-1 升到 m3-2，并同步记录在 turn 与日志中，方便区分修复前后的样本。

### 验证

先补回归测试再修实现：原实现实际出现“NONE 被保存”和“持续 NONE 仍标为 COMPLETED”两个预期失败。修复后分别验证模型修复为 UNKNOWN、持续错误时无结果落库、正常 S00 的 NONE 仍可接受。使用模型响应替身控制异常，但状态与落库走真实隔离 SQLite。

修复后有限 LIVE 复测中，S05 首问与追问均返回 UNKNOWN、无重试建议。本次 LIVE 没触发修复分支；该异常分支的证据来自确定性回归，不能说真实模型已实测触发并修复了错误结果。

### 面试口述示例

“我在 FlowLens 的真实多轮验收里遇到过一个 JSON 完全合法、业务含义却错的问题：失败任务的正文说根因未知，但枚举返回正常。之前的 schema 校验和 Mock 都没暴露它。我先保存真实失败样本，再用模型替身复现，发现缺少运行状态与诊断原因的语义校验。修复时让服务端校验事实，给模型一次纠正机会，仍不合规则明确失败、不落结论，同时保留正常任务的回归。这个经历让我把字段合法、业务合法和自然语言质量分开验证。”

可展示：[Agent 实现](../apps/server/src/diagnosis-agent.ts)、[回归测试](../apps/server/test/m3-guidance.test.ts)、[M3 真实复核记录](m3-acceptance-plan.md)。

## 案例二：界面标记模拟，模型却暗示能验证真实系统

### 现象和影响

S04 的审批/模拟重试链路是正确的：资格由后端判断，人批准后创建唯一 child。但是修复前真实回答提出“申请一次模拟重试以验证上游是否恢复”。本项目没有真实上游连接，child 的结果来自 fixture，因此该建议把演示状态流转误说成了真实恢复验证。

### 定位与修复

原 Prompt 说明了 FIXTURE 与不能执行真实重试，但没有把“模拟结果与外部服务健康之间不存在证据关系”明确提供给每轮模型。界面上的来源标识也不能保证模型自然语言自动遵守边界。

补充 `execution_semantics`：任务数据来源 FIXTURE、重试模式 SIMULATED、结果来源 FIXTURE、不能验证真实上游。提示明确禁止把模拟成功解释为真实服务恢复、任务修复或模型修复有效性；同时保留后端重试资格与人工审批，模型只提出建议。没有泄露 scenario_id、retry_timeline 或把评测答案注入模型。

这里可确定性验证的是模型收到的事实与操作资格；任意自然语言是否产生错误暗示，不能用一组关键词过滤或假网关回答证明。所以离线验证之后，仍在已授权额度内用真实模型复测同一流程。

### 结果与剩余限制

修复后 S04 的真实回答明确说“该重试仅为模拟，不验证真实上游可用性，也不代表服务或任务已恢复”，建议只用于演示审批与状态流转。批准后 child 模拟成功，追问返回 ALREADY_RETRIED，未再提出重试；数据库仍只有一个 child 与一个 execution。

但本次建议理由中仍出现“批准不等于授权”的不准确措辞：人批准会授权该次模拟执行，模型建议本身才不等于授权。S05 也把一次检索所得的超时条目概括为“手册仅覆盖上游超时”，未反映仓库还有其他手册。这些是保留待人工复核的自然语言问题，不把主要目标通过写成所有回答无误。原 12 次调用额度已用完，未追加验证。

### 面试口述示例

“另一个问题发生在模拟与真实的边界上。虽然页面写了演示数据，模型仍建议用模拟重试验证真实上游恢复。我把这个错误保留为真实验收样本，补了每轮可读的执行事实，明确模拟结果只能演示审批和状态流转。再用真实模型走审批前后流程，确认主要误导没有重现。我没有因此宣称模型准确率提升或真实任务被修复；这是一个受限样本的质量修复，审批与幂等正确性仍由确定性服务端实现保障。”

## 案例三：真实模型误把模拟任务说成模拟模型

用户启用持续 LIVE 后，开发页面已由 DeepSeek 返回真实回答，但询问“现在使用的是真实模型吗”时，模型仍说“不具备访问真实模型”。页面和数据库的 provider_mode 均为 LIVE；不是切换失败。Agent 每轮只提供 FIXTURE/SIMULATED 执行事实，没有独立提供当前模型来源，存在输入信息缺口。不能声称已经知道模型内部为何产生该句。

修复时分别提供模型来源与执行语义：`model_source` 描述本轮 provider_mode/model，`execution_semantics` 继续说明模拟数据、模拟执行与不能验证真实上游。提示禁止因任务模拟而否认真实模型，版本升级 m3-3。LIVE/MOCK 两条离线回归先失败后通过，证明两种来源事实都能独立传入；实际相同问题的 DeepSeek 复测已准确说明真实 API，S05 仍保持 UNKNOWN、无重试建议，页面刷新恢复正常。

这次没有用前端替换模型原话，也没有关键词过滤冒充自然语言质量保证。失败回答保留在原会话和 `ongoing-live/`，复测保存在 `ongoing-live-fixed/`。本次只是一个问题的有限真实样本；旧记录不会因修复自动变成正确回答。

面试可说：“接入真实模型后，我发现 UI 正确显示 LIVE，模型却否认自己使用真实模型。我对照服务端来源和实际结果，发现传入上下文只有模拟任务事实，缺少模型来源。我把模型、数据、执行三种来源分别传入，先验证上下文，再用真实 API 复测原问题。这个问题说明页面标签正确不代表模型理解一致，也不能用 Mock 固定回答替代真实验收。”

## 案例四：Agent 工具权限与平台功能被混为一谈

用户真实验收 S04 时，首轮建议批准后模拟重试，追问“执行一次模拟重试”却回答“无法在此环境执行模拟重试”。核对开发数据库后确认资格有效、两轮都有建议、无审批或 child，实际流程没有执行失败，问题在文案与能力上下文：Agent 只拥有只读工具，但平台在 UI 人工批准后有独立模拟器。原上下文没有明确描述这条执行路径，模型将自身工具限制说成整个环境的限制。

m3-4 增加每轮审批路径事实，明确平台有模拟执行能力、Agent 不能自行执行/批准、聊天不代替按钮。合资格请求应提出建议并引导“申请重试”→“批准模拟重试”。保留服务端资格校验、按钮审批、唯一 child 与只读工具边界，没有为解决文案问题增加模型执行权限。

新增离线回归先失败后通过，并用真实隔离 SQLite 验证聊天与申请不创建 child、批准才创建一个。随后独立任务的真实三轮复测通过主要目标：按钮引导正确，批准后唯一模拟 child/execution，原运行不能再次建议重试，刷新恢复正常。实际 3 次 API 请求、6,995 tokens；原用户运行未被测试批准。样本在 `approval-workflow-live/`，定向 10/10、全套服务端 68/68 与前端 14/14、typecheck/lint/build 通过。

面试可说：“用户验收发现模型先建议批准重试、随后又说环境不支持。我查数据库发现建议与资格都正常，执行也根本没开始。问题是模型把自身只读工具与平台审批后的模拟执行能力混淆了。我补充了审批流程事实，并明确让它引导两次按钮，既没有放开模型权限，也没有把一句聊天当成人工批准。再用真实模型和隔离数据库走批准前后流程，验证只有按钮批准才创建新运行。”

仍需保留限制：真实复测首轮未经充分证据排除配置/数据原因；原运行工具不读取 child 状态，模型不能据此报告新运行已成功。平台结果需要查看新运行，有限样本不能宣称所有措辞准确或阶段已验收。

## 案例五：证据按钮重复点击只重载，没有收起

用户确认刷新完整后提出：同一证据按钮第一次点开，第二次应收起。原前端每次点击都重置并请求证据，既有关闭按钮/Escape 测试未覆盖再次点击触发按钮。新增 Chrome 场景在原实现实际失败：二次点击后仍有一个浮窗。

最小修复是在请求前检查当前 anchor，同一按钮走关闭路径；关闭时清理加载/错误状态，并沿用现有请求序号防止晚到结果影响关闭后的状态。回归同时覆盖已加载与加载中关闭、不同证据切换、关闭按钮/Escape、对话保留。前端 14/14、typecheck/lint/build 与 Chrome 全套 13/13 通过，当前开发页历史 S05 两轮开关核对也通过。没有模型调用、服务端或持久化变更，用户原修改保留。

可用于讲解如何根据实际交互补测试，以及为什么异步浮窗关闭不止是隐藏元素，还要处理晚到响应。不能声称本次发现了旧截图采集超时的根因；那是另一个尚未定位的记录。证据在 `evidence-toggle-{red,green,e2e}.txt` 与 `evidence-toggle-dev/`。

## 持续调用配置的变更记录

用户后续明确授权持久 LIVE 与取消总请求次数上限，旧规则只接受 1–12 次，持续对话会被总额挡住。将请求预算提取为独立模块，显式 `unlimited` 才取消总次数限制；保留批准标志、有限次数模式和单轮模型/工具/超时限制。六条预算测试覆盖未授权、非法预算、有限额度、超过 12 轮的对话以及无限工具循环仍被终止。用真实 SQLite 和注入网关测试，不把 13 轮替身测试写成真实 DeepSeek 调用。

本机 `.env.local` 持久启用 LIVE，每次输出仍最多 2048 tokens；密钥未进入仓库。该配置是本地单用户、明确授权持续付费的演示选择，不是生产额度管理：有限模式仍是进程内计数，重启会重置，日志 token usage 也不是实际金额。最新全套离线服务端 67/67、前端 14/14，typecheck/lint/build 通过；原 12 次有限复核是历史记录，后续持续授权另行记录。

引用浮窗还出现过采集脚本超时：首次在全页截图后等不到关闭按钮，根因未完整定位；将关闭按钮与 Escape 检查放在截图前，本次 MOCK/LIVE 均通过。这可用于说明如何区分测试工具问题与产品问题，但不能作为“已定位并修复某个前端 Bug”的案例。

## 案例六：有引用，不等于引用能支撑结论

M4 六问预演发现 Mock S00/S05 的 cause 正确、引用 ID 也有效，却引用了 Starting read step。这条日志不足以支撑成功或未知根因。新增两个回归先失败，改为引用服务端预读的终态 RUN_STATE 后通过；独立评测仍核对原来源内容，而不是仅检查 ID 存在。

真实 DeepSeek 基线的 S04 同样只引用预读状态，没有调用日志工具。m4-1 增加 Prompt 提醒后仍未取得最低日志证据。m4-2 增加服务端已知失败原因的 LOG 引用门槛，沿用一次修复，让模型继续动态查询日志；新增回归先失败、修复后验证完整三次模型循环及真实 ERROR 日志。最终两问和批准后追问各经历一次修复，再调用 get_task_logs 完成，不能说 Prompt 已让模型第一次就正确查工具。

面试可以讲“ID 合法性、来源真实性、结论相关性是三件事”。当前服务端只保证 LOG 类型与会话来源，独立评测检查超时文本；没有实现任意自然语言的通用事实证明器。修复会增加调用和延迟，最终 S04 约 4.35～4.69 秒，不能声称降本提速。

## 案例七：JSON 结构与判断状态必须分别校验

真实基线 S05 第一问连同一次修复都产生不合法 JSON：next_steps 数组提前关闭，后面出现游离字符串；服务端明确 FAILED / INVALID_RESULT，没有保存结论。第二问 cause=UNKNOWN 却 evidence_status=SUPPORTED，存在“根因不知道、界面却显示有证据支持”的矛盾。

网关按 [DeepSeek JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/) 增加 response_format=json_object，仍保留解析、schema、来源及修复校验；提供结构示例与简短回答约束。UNKNOWN 必须 NEEDS_CONFIRMATION，违反时修复一次，重复违反则明确失败，不静默替换模型答案。新增测试先复现缺少请求配置及未知状态被接受，修复后验证正确修复和拒绝分支。真实 m4-1、m4-2 六问中格式和未知状态错误未重现；JSON 模式不保证业务事实正确，也不承诺永远不返回空内容。

## 案例八：原环境能运行，干净安装却失败

最初干净目录 install 已从缓存复用全部依赖，退出非零的实际原因是 pnpm 11 默认严格检查未明确允许的构建脚本，出现 ERR_PNPM_IGNORED_BUILDS（esbuild）。不是网络或缓存缺包。仓库新增 allowBuilds: esbuild: true，保留其他依赖的默认检查；按锁文件在新的无 node_modules 目录重新安装通过。依据 [pnpm 构建配置](https://pnpm.io/settings/build)。

启动验证工具本身还把 pnpm exec 当成 pnpm run，导致 npm_execpath 缺失、没启动服务；改成实际 check:start 脚本并支持 pnpm 原生 exe。这个是验证工具问题，不能冒称修复了产品启动失败。使用隔离端口、MOCK 环境和独立数据库，避免已有开发进程掩盖问题。

## 案例九：创建会话期间的输入时序

新目录 Chrome 全套回归曾在发送响应丢失用例的第一次发送前超时：创建新会话后立即填写，最终输入框为空、发送禁用。尚不能从单次失败证明浏览器事件丢失的内部细节。进一步用受控延迟创建请求确认：旧会话输入框在 busy 期间仍可编辑，可能进入即将被替换的输入区。

在 busy 时禁用 textarea，保留模型运行时继续写草稿的既有行为；新回归先失败（旧输入仍 enabled），修复后确认创建期间 disabled，新会话快照返回后 enabled 且可填写。原发送响应丢失的幂等断言未删除或放宽，完整回归结果以 P0 报告为准。可讲清“用户可编辑状态要与异步操作状态一致”，不要将推测的内部事件机制当成已证实根因。

## 案例十：从工具执行记录到可查看、可恢复的轨迹

按 PRD §5.5 复核时发现：工具卡已有名称、状态、错误，却没有完整的参数/结果、用途与耗时。服务端的结果摘要也仅有行数，因此刷新后无法还原查询输出。集成测试先复现输出未保存，再补齐结果持久化与 SSE 的可选 output 字段；沿用工具注册表的输出大小上限，运行日志仍只记白名单元数据，不默认输出查询正文。

前端以通用卡显示用途、调用 ID、开始时间和耗时，展开 JSON 参数及结果；用 Vue 文本插值避免把查询正文当 HTML。消费者验证新增字段类型后才推进游标，覆盖重放去重、历史行数摘要、未完成/失败状态及陌生工具名。Chrome 检查真实日志工具详情、注入陌生名称后的通用展示与刷新恢复。旧库无需迁移，缺失的历史完整结果不补造。最终服务端75/75、前端17/17、Chrome16/16；该轨迹补齐使用离线验证，未追加 DeepSeek 请求。

面试可以围绕生产者、持久化、事件、消费者和历史数据逐层说明：新增字段采用可选契约，但一旦提供就严格校验，避免只改 UI 或只改事件导致刷新前后行为不同。

## 案例十一：流式初稿和可发布答案的边界

用户复核发现，发送消息后先出现一版回答，随后消失并替换。其实际 turn 中存在 message.reset：初稿的已知超时结论只引用 RUN_STATE，服务端要求补齐 LOG；原前端从流式 JSON 提取 summary 并显示，即使旁边写了“尚未完成”，仍容易被当成已回答。

用户明确要求只看到最终答案，并逐步显示。新增回归先复现初稿暴露和最终全文直接跳出；调整为校验前只显示进度，校验完成后由前端分批呈现最终的 summary、findings 和后续建议，引用在相关文字完成后出现。保留原始 SSE 协议及后端校验，避免为了画面稳定而取消证据约束。历史直接恢复，同一 turn 的快照/事件结果 ID 替换不重播，离开会话清理计时器，减少动态效果偏好直接显示全文。

前端21/21、Chrome MOCK17/17、typecheck/lint/build通过，浏览器验证包含拒绝初稿、reset、最终事件、重复快照与刷新。本次没有新增付费请求，旧 LIVE 录屏属于调整前。取舍必须讲清：正文开始需要等待完整生成与校验，视觉渐进展示由前端完成，不能把它当作 provider 首 token 或推理提速指标。面试重点是区分生成、校验、发布和历史恢复这几个状态。

## 案例十二：测试服务自动换端口导致启动超时

版本交付时，独立目录两次在 Playwright webServer 启动阶段超时，测试尚未执行。单独启动 Vite 却在约300ms内就绪。开启 pw:webserver 日志后确认：5174被外部进程的出站连接占用，Vite 自动改用5175，测试仍请求5174。只检查 LISTENING 看不到该占用；Windows 连接状态为 Bound/Established。

配置调整为前端测试端口由操作系统分配，启动命令和探测 URL 使用同一个端口，启用 strictPort 避免再次悄悄切换；保留 FLOWLENS_E2E_WEB_PORT 以便显式覆盖。API仍用隔离端口4174。未关闭外部程序、增加超时时间或放宽用例。该问题属于测试启动配置，不能冒称修复了诊断或任务执行故障；首次失败及调试输出保留在 `logs/m4/clean-f0b4807977a344f6a96fa8bddbad9a6f/`，最终结果见版本交付记录。

修改中的首版动态配置还遇到 worker 重新加载配置时各自选端口的问题，17项实际连接失败，记录在 `clean-605fd0ec325a446e811860efc32d56d5/`。随后将 runner 已选端口通过环境变量传给 worker，定向浏览器流程通过；没有将首版配置称为有效修复。可用这个案例说明进程间共享启动配置的必要性，而不是把测试工具故障当成业务故障。

## 案例十三：评测脚本把上一轮证据当成当前轮证据

最终答案改为逐步展示后，离线评测在数据库结果已保存时立即点击页面最后一个引用按钮；当前轮正文仍在展示，引用尚未出现，脚本选到了上一轮按钮。第二次点击时当前轮按钮已出现，选择目标变化，原浮窗没有按预期关闭。实际失败保留，未改产品引用开关或评测答案。

评测改为等待当前诊断卡 aria-busy=false，并将引用选择器限定到该卡。新增 final_answer_visible_ms 单独记录答案展示完成时间，原 elapsed_ms 仍保留原测量含义。随后隔离 MOCK 六问的原因、来源、最低证据均6/6，工具12/12、未知原因保留2/2，付费请求0；最终完整 Chrome 17/17。面试可说明数据库结果就绪与页面交互就绪是不同状态，自动化必须等待操作目标的真实状态。

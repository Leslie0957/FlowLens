## 诊断场景深化与项目定位

记录日期：2026-10-09。状态：未开始，本次仅记录定位、建设方向和验收要求，不新增功能或改写已完成验收。

定位：当前 SQL 列错误和输出契约错误适合验证完整流程，但错误线索较明确，尚不足以充分展示 Agent 区分根因的能力。已有工程深度主要来自 SSE 状态恢复、异步竞态处理、证据与版本绑定、人工审批、执行校验、事务入库、幂等和增量撤销。后续提升应让实际场景体现取证和判断，不以增加工具数量、强制多轮调用或堆叠技术名词作为完成依据。

目标：在保持当前本地合成数据与受控执行范围的基础上，优先打磨至少一个“相同现象、不同根因，需要追加证据才能区分”的完整场景，再扩充少量有代表性的变体。先验证 Agent 在没有历史检索时的诊断能力，再与下方 RAG 待办衔接；RAG 提供历史经验，不能代替当前执行取证。

### 场景设计与真实来源

- [ ] 基于 ADR 排障材料梳理可借鉴的问题类别：必填字段缺失或为空、SQL 输出与结果处理字段映射不一致、同键不同内容、短暂写入冲突等。用合成数据重建选定场景，注明是流程借鉴、问题类别对应还是具体机制复现，不把所有 ADR 故障都称为已覆盖。
- [ ] 优先设计“输出或目标车系字段为空 / 不符合要求”的场景族，区分源数据为空、SQL 输出遗漏或别名错误、结果处理字段映射错误等原因。先确定哪些变体能由现有工具观察、哪些需要补充真实只读信息；未建模的处理环节不能靠虚构日志制造根因。
- [ ] 每个变体记录触发条件、实际失败阶段、可观察信息、区分其他原因所需证据、允许动作及修复后的验证依据。错误码和首条日志描述真实现象，不直接附上预设根因或标准修复答案。
- [ ] 保留当前基础样例作为正常流程和异常回归入口。新增场景不要求全部故障都能通过 SQL 修复；字段映射或输入问题可能需要人工处理，写入冲突是否可重试必须有明确依据和独立授权范围。

### Agent 取证与动作判断

- [ ] 让模型根据真实执行状态、SQL、表结构、日志、输出和任务契约逐步排除原因。只有确实缺少信息时才继续读取，工具轨迹应能解释新增观测如何影响结论；证据已经充分时允许直接结束，不强制固定工具顺序或调用轮数。
- [ ] 设计相同表面报错下的不同工具反馈，验证实际返回会改变后续取证和最终判断。不能只让模型按模板读完工具，再输出预先约定的答案。
- [ ] 明确区分已观察事实、根因假设和信息缺口；证据不足时输出待确认项或人工处理建议，不以引用合法代替语义正确，也不把无进展重复读取算成有效调查。
- [ ] 明确 SQL_PATCH、RETRY_SUGGESTION、MANUAL_REQUIRED 等动作的适用范围。SQL 候选继续受具体审批、版本检查、单次实际执行及独立结果校验约束；重试建议本身不等于获得执行权限。
- [ ] 必要时补充最小范围的只读证据，例如实际字段映射配置、入库前检查报告或受限目标数据观测。新增工具仍需绑定项目、执行和版本，保持输出限制及证据追溯，不扩大为任意代码读取、Shell 执行或自主修改后端。

### 验证与面试表述

- [ ] 为场景建立独立预期：正确问题类别、必要区分证据、合理动作和修复验证结果。预期来源于合成输入、明确契约及确定性检查，不由模型自评，也不直接泄露到诊断上下文。
- [ ] 用可控模型测试取证循环、反馈回写和拒绝分支，用实际 SQL、SQLite 及工具返回验证场景确实发生。覆盖同症状不同根因、信息不足、引用错误、错误候选、版本变化及无需修改 SQL 的情况。
- [ ] 在后续获得 LIVE 调用授权后，以固定样例记录真实取证路径、判断正确与否、错误修复建议、证据充分性及调用成本；如实保留失败样本。MOCK 证明流程约束，有限 LIVE 样本不能推导生产准确率。
- [ ] 保存至少一条可演示的完整轨迹：现象出现 → 初始信息不足 → 工具补充区分证据 → 确定原因或保留不确定项 → 选择处理方式 → 实际验证 / 人工处理交接 → 历史回溯。历史检索接入后，用相同场景与无检索基线对照，不用工具次数更多证明效果更好。
- [ ] 完成后再更新面经和对外表述。当前口径保持“排障样例较基础，工程流程完整”；后续只讲实际验证过的根因区分与处理能力，不宣称已覆盖生产中的通用复杂排障。

验收标准：至少一个完整场景族能用真实可观察信息区分多个合理原因；模型后续读取和结论确实受工具反馈影响；可修复问题经实际校验，不适合 SQL 修复或信息不足的问题不会被强行修改；轨迹、原始证据、失败情况和能力边界均可复查。仅增加复杂错误文本、工具数量或向量数据库不算场景深化完成。

## 帧级合成数据与连续低速片段挖掘

记录日期：2026-10-09。状态：未开始，后续场景深化时实施。本次仅记录计划，不生成新数据或修改执行逻辑。

目标：把当前“一行一个预设事件，按速度和时长筛选”的简化输入，扩展为“同一采集样本内有多帧速度记录，SQL 识别连续低速并输出事件范围”。借鉴 ADR 的帧级数据与 CLIP 输出思路，先完成一个低速场景；业务规则自行明确，不复刻公司的真实标签口径，也不把阈值命中直接等同于不良驾驶。

- [ ] 构建固定种子的合成帧级数据：样本 ID、帧号、微秒时间戳、速度和车系；明确采样频率、样本边界及时间单位。首批可用约 60 秒的样本，包含正常速度、单段低速、多段低速和无命中等情况，不需要真实视频或图像。
- [ ] 定义事件分段契约：速度阈值、连续性判断、最短持续时间及起止时间语义。明确缺帧、时间间隔过大、重复帧和乱序数据如何处理；先按断点分段，不将分散低速时长直接累加，不跨样本合并。持续时间计算与采样间隔、边界语义保持一致。
- [ ] 用 SQLite 支持的 SQL 实现帧筛选、连续性分组、事件聚合和时长过滤，输出 `dat、st、et、car_series`。同一样本可输出多个事件；仅输出片段位置，不物理裁切数据文件。先完成基础 CLIP 场景，暂不加入复杂场景豁免、时间外扩或 FILE 粒度。
- [ ] 从合成时间线和独立参考逻辑建立预期事件范围，核对事件个数、归属和起止边界。覆盖恰好 3 秒、不足 3 秒、速度恰好为阈值、多个不连续短段、样本首尾及缺帧等边界；无命中可以是合法结果，不能仅凭 0 行就启动失败诊断。
- [ ] 与上方“相同现象、不同根因”场景建设衔接：设计 SQL 连续性分组错误、速度或时间单位使用错误、源数据缺帧等真实变体。明确实际异常如何触发执行或校验失败，模型初始信息不直接泄露根因；输入问题允许建议人工处理，不能强制全部通过修改 SQL 解决。
- [ ] 按场景需要提供最小范围的 MCP 只读观测，例如指定时间范围的帧预览、采样与单位说明、缺帧统计和输出事件范围。读取仍由后端绑定项目、执行和输入版本，限制范围、条数及字节量，登记证据；模型依靠追加观测区分原因，不把整段数据默认塞进上下文。
- [ ] 复用现有候选审批、实际 SQL 执行、独立校验、事务入库、增量撤销和历史追溯。补充确定性单元与集成测试、完整浏览器流程，再进行真实模型验证；完成后更新面经的数据场景描述。

验收标准：能从同一样本的真实合成帧记录中识别多个连续事件，输出正确时间范围并处理约定的边界；至少一组诊断变体需要追加帧或规则证据才能区分原因，修复经实际执行校验，入库与撤销可回溯。仅增加数据条数或复杂 SQL 长度不算完成。

## 向量数据库 RAG 历史案例检索

记录日期：2026-10-09。状态：未开始，面试准备后实施。本次只记录需求与验收范围，不新增功能、依赖、模型调用或数据库迁移。

目标：将实际排障历史沉淀为可维护的案例，通过 Embedding 和向量数据库检索相似故障，再把检索结果与当前执行证据交给 Agent，形成“历史案例检索 → 当前证据核对 → 诊断与修复候选 → 审批验证 → 案例沉淀”的完整 RAG 链路。

### 案例沉淀与维护

- [ ] 定义结构化案例：问题现象、失败阶段、错误码、关键日志、确认根因、处理步骤、SQL Diff、验证结果、适用表结构 / 业务规则、来源项目与执行、证据 ID、案例版本和确认状态。
- [ ] 从实际执行、诊断、候选、审批与验证记录生成待确认案例，支持人工编辑、确认、归档与去重；保留原始历史，不把模型推测直接标为已确认根因。
- [ ] 区分已验证解决、修复失败和根因待确认；旧故障手册可作为补充知识导入，但明确标识来源，不能当作实际成功案例。控制入库内容范围，不把密钥、无关原始数据或完整模型上下文直接送去生成向量。

### Embedding 与向量数据库

- [ ] 完成 Embedding 模型和向量数据库选型。使用真实向量数据库存储向量并执行相似度检索；普通 SQL 关键词查询、静态手册匹配或仅向量化而不检索不算完成。具体引擎和模型在实施时确定。
- [ ] 设计案例分块和检索文本，保留 case_id、chunk_id、案例版本、来源、确认状态、项目范围及适用条件等元数据；记录 Embedding 模型版本、维度和内容 hash。
- [ ] 实现新增 / 更新 / 归档的索引同步、内容去重、批量回填、失败重试与索引重建；模型或维度变化时支持重建，案例正文与向量索引不同步时不返回失效内容。
- [ ] 实现语义相似度检索及元数据筛选、Top-K、相关性门槛、同案例去重和返回长度上限；明确检索分数的含义。按需结合错误码 / 关键词形成混合检索，仍须保留并实际使用向量检索。

# FlowLens 真实 Pipeline Demo 实施计划与 AI 交接

## 1. 最终目标

把 FlowLens 的演示主线改为一个真实数据任务：用户选择或编辑 SQL，执行车辆事件查询与输出校验，查看预检结果后人工批准入库；发生真实错误后，Agent 查询 SQL、表结构与执行证据，提出修改或其他处理建议；前端展示诊断、证据、Diff 和审批；批准候选后在隔离环境实际验证，结果合格才作为新版本继续使用。每次真实入库保存业务数据快照，提交失败自动回滚，提交成功后支持撤销最新有效批次。提供独立只读 SQL 查询页检查源数据、目标结果和历史快照。

这是受长安实习中“SQL 查询 → Python 处理与校验 → 幂等入库 → 人工排障”启发的独立本地 Demo。使用自行生成的车辆事件数据，不接公司环境，不复用公司凭据，不声称复刻完整实习产线。Demo 编排可以继续用 Node.js，不要求为了贴近实习改写整个后端为 Python。

完成后用户应能讲清楚三个能力：

1. 数据任务真实执行与故障来源：查询成功不等于入库成功，程序结束不等于数据正确。
2. Agent 基础：模型通过有界工具循环取证、形成结构化建议，平台限制能力并验证候选。
3. 前端基础：任务状态、SSE、日志、工具轨迹、证据、Diff、审批及验证结果联动；切换与断线不串数据、不重复操作。

## 2. 首版范围：保持小而完整的演示链路

### 必做

- 一种任务：车辆低速事件候选查询与入库，业务条件由项目预先固定。
- 固定本地运行器实际执行 SQL、校验输出、转换并写入目标表。
- 三个可重复的核心案例：SQL 列错误、输出字段契约错误、重跑不重复入库。
- 可编辑 `task.sql`，其他配置与验证逻辑只读。
- Agent 实际查询 SQL、Schema、日志及校验证据，返回候选或明确的非修改建议。
- Diff、单次人工批准、隔离验证、新版本、原失败历史。
- 查询/校验预检与正式入库分开；入库批准绑定 SQL、输入、结果及目标数据版本。
- 提交失败事务回滚；提交成功后可由后端撤销最新有效批次，恢复入库前业务表数据。
- 独立只读 SQL 查询页：源表、目标结果、指定入库前快照、字段结构、查询结果和批次定位。
- 主流程 SSE 状态同步与前端请求隔离。
- 至少一个真实模型样本演示；确定性 Mock 用于自动化与异常分支。

### 本轮不做

- 公司数据库接入、ClickZetta 驱动适配、生产权限、多租户或公网部署。
- 任意仓库、任意 Python/JS/Shell 修复、通用任务调度平台。
- 自由数据库管理、任意 DDL/DML 或模型修改源数据、表结构、验证器。
- 完整七字段生产身份、复杂增量水位、并发提交冲突模拟器。
- 向量库、多 Agent、长期记忆、checkpoint/Continue。
- 新的自动修复循环；已有有限循环可以保留为旧实验，本轮先完成单次批准和验证。
- 重做所有页面、引入大型 SQL IDE 或 Diff 编辑器。

首版的非修改路径只需明确表达“建议重试/需人工确认/没有候选”，并保持无修改。没有实现的复杂故障不得用固定假日志冒充真实执行。瞬态冲突重试、水位等能力作为后续项目，不阻塞 Demo。

## 4. 演示任务与数据约定

### 4.1 数据库

每个项目保存一份版本化、只读的源数据数据库，以及可实际入库的目标数据库。每次执行保存 SQL/输入版本与对应 hash，避免历史记录随当前文件变化。

推荐源表 `raw_vehicle_events`：

| 字段 | 含义 |
|---|---|
| event_id | 输入样本 ID |
| dat | 自行生成的数据片段名称 |
| start_us / end_us | 事件时间，微秒 |
| speed_mps | 速度，米/秒 |
| car_series | 合成车系标识 |

使用多条合成样本：低速/正常速度、足够/不足时长、时间边界。数据数量无需大，但必须有不应入库的对照样本。样本可重复生成，并保存版本；不照搬公司数据标识。

既定任务规则示例：筛出 `speed_mps < 1` 且持续时间至少 3 秒的候选。明确这是 Demo 规则，不是生产负向驾驶算法。规则和期望键集合由可信验证器独立表达，模型不可修改。

SQL 输出契约固定为 `dat、st、et、car_series`。运行器检查字段、类型、非空和 `st <= et`，转换后入库。

首版正常 SQL 可采用：

```sql
SELECT dat, start_us AS st, end_us AS et, car_series
FROM raw_vehicle_events
WHERE speed_mps < 1 AND end_us - start_us >= 3000000;
```

允许范围限定为单条 SELECT、指定源表、字段/别名以及上述所需的有界比较与算术表达式；通过结构化解析或完整小语法检查，不靠 `startsWith('SELECT')` 或关键词黑名单。首版不必支持 JOIN、CTE、子查询或多语句。禁止模型或用户任务 SQL 执行 ATTACH、PRAGMA、DDL/DML、扩展加载及任意文件/网络能力。目标写入只能由可信运行器参数化完成。复用并调整现有超时、日志/返回体上限和每次预览行数限制。

推荐目标表 `mining_results`，保留上述字段、task_id 与首次写入的 execution_id。Demo 业务唯一键用 `(task_id, dat, st, et)`，明确是简化身份，不冒充实习七字段模型。同键同内容跳过；同键不同内容显式报冲突，不覆盖旧记录。技术修复的代码 revision 不自动改变业务身份，避免每改一次代码就新增一份重复结果。

任务执行的查询/校验预检只保存输出和校验结果，不自动写项目目标库；用户批准入库后，由可信代码事务写项目目标库。验证候选只能写独立验证库。源数据只读、运行器固定，模型不决定写入 SQL。

### 4.2 真实故障案例

| 案例 | 如何真实触发 | 应看到什么 | 合格的处理 |
|---|---|---|---|
| A：列错误 | 任务 SQL 使用源表不存在的 speed_kph，既定规则仍是 m/s | SQLite 实际异常；查询阶段失败 | Agent 查 Schema，使用正确字段与既定规则，批准后验证 |
| B：输出契约错误 | SQL 将 car_series 输出别名写成 vehicle_type | 查询成功，输出校验因缺 car_series 失败，目标库无新记录 | Agent 对照 SQL、实际输出与契约，修正别名 |
| C：重跑 | 对同一源数据和任务再次执行正常版本 | 实际再次查询、校验、入库，记录新增/跳过数 | 目标表键集合与总行数不变，无重复写入 |
| D：候选语义错误（自动化必测） | 可执行 SQL 放宽筛选条件或改错时间范围 | SQL 可执行，独立规则/键集合校验不通过 | 不发布该候选，不污染项目目标库 |
| E：入库中途失败（自动化必测） | 隔离测试夹具让目标约束在部分 INSERT 后实际失败 | SQL/校验通过，但事务写入失败 | 事务回滚，全部业务数据与入库前一致，无半批结果 |
| F：人工撤销 | 已批准且提交成功，用户复查后认为本次结果不应保留 | 查询页可以核对本次实际新增行 | 撤销最新有效批次，恢复前状态，保留审批/提交/撤销历史 |

案例 A 不是“把 speed_kph 改名就肯定正确”：独立业务规则还检查单位与筛选条件。验证应能拦住结构正确但语义错误的修改。

模板只负责提供初始代码和数据。日志、错误、结果与状态均来自真实执行，不手工编排成功/失败时间线。用户修改或重新执行错误代码，仍应实际失败。

## 6. Agent 首版能力要求

建议只读工具，名称可按实现调整：

| 工具 | 返回内容 | 用途 |
|---|---|---|
| get_execution | 状态、失败阶段、错误、分阶段行数 | 确认现场 |
| get_sql | 当前失败版本 SQL、hash | 找到可修改对象 |
| get_schema | 本次执行实际源表/目标表结构 | 识别字段与类型 |
| get_logs | 本次执行实际有界日志 | 定位具体异常 |
| get_output_preview | 实际输出字段、少量合成样本、校验拒绝原因 | 区分查询成功与契约失败 |
| get_task_contract | 既定规则、输出要求、业务键 | 明确修改与验证边界 |

工具绑定 execution/revision/input hash；模型不能指定其他项目、任意路径、数据库或命令。登记证据来源、版本、定位与摘录，前端可点开。当前 Schema 应从本次使用的数据库读取，不用 Prompt 里的硬编码列名充当查询结果。

Agent 采用有限工具循环：将工具描述交给模型，执行模型选择的合法查询，把结果返回模型，再形成最终建议。不能在后端直接替换字段名、返回预写答案，却在界面标为 LIVE Agent 修复。

最终结果至少包含：失败阶段、结论、引用、处理类型，以及可选候选。处理类型为 `SQL_PATCH / RETRY_SUGGESTION / MANUAL_REQUIRED / NO_CHANGE` 等有界枚举。非修改建议允许不产生候选；不能遇到什么错误都强迫重写 SQL。

结构与引用由服务端校验；语义正确性最终依靠实际验证。保留合理的单轮请求、工具、输出与时间预算，不新增无限尝试；不得通过删校验、自动填证据或硬改答案使验收通过。

仅允许修改 `task.sql`。表结构、源数据、任务规则、运行器、依赖和验证器不可修改。业务筛选规则在演示里已定义，候选不得通过改变业务要求取得成功。

## 7. 批准、验证与版本状态

建议流程：

```text
原版本真实执行失败
        ↓
Agent 取证、保存待审批候选
        ↓
页面显示服务端 Diff 与引用
        ↓
用户批准这一份候选
        ↓
创建不可变候选版本，启动隔离验证
        ↓
真实执行 + 独立结果校验 + 重跑无重复检查
        ↓
通过：设为当前可用版本
失败：保留候选和验证记录，当前版本不变
```

候选批准和验证是不同事实，批准候选后应先显示验证中，不能直接成功。验证通过也不表示已经写项目目标库：用户运行当前版本完成只读预检，查看新增/跳过/冲突预览后，再批准这一次入库。界面分别使用“批准修复并验证”和“批准本次入库”，不要把模型修复授权、验证成功与数据提交混成一个状态。

候选批准绑定任务、基准版本/hash、候选 hash、固定验证入口和有效期。候选版本与验证 execution 各只创建一次。发布时再次比较当前基准版本，若验证期间项目已经改变则标过期/冲突，不覆盖新版本。启动或发布失败写可解释终态，不自动重复执行副作用。

验证库复制或重建时记录源数据和目标初始状态；允许可信代码创建，模型不可直接写入。使用可信验证器按源数据和既定规则计算预期键集合、字段值、时间范围，不用候选 SQL 自己的输出当答案。

## 8. 前端要体现的重点

首版以“任务—执行—诊断—验证”为清楚的信息层级，主页面包括：

- SQL 与版本：可编辑当前草稿，运行历史显示对应只读版本。
- 执行步骤：查询、校验、入库、验证的真实状态和行数，突出失败步骤。
- 日志：按执行切换，可从引用打开上下文或目标记录。
- Agent：工具开始/完成/失败，参数与有界结果，校验后结论与来源。
- Diff 与批准：展示本次修改，区分待批准、已拒绝、验证中、验证失败、已通过。
- 结果：独立断言、实际入库/跳过/冲突数、目标表预览与旧运行入口。
- 入库批准：待写数据与增量预览，明确展示本次作用范围；批准后显示实际提交状态。
- 撤销：最新有效入库批次展示“一键撤销本次入库”，显示恢复范围与执行结果；历史审批与原运行保留。
- 数据查询：独立只读 SQL 查询页，支持从证据、执行、入库批次与恢复结果跳转。

继续使用 Vue3、TypeScript、Pinia/组件状态与 Element Plus。不要把所有请求塞进一个大组件；可适度拆分步骤条、日志、诊断、Diff 和结果组件。简单 textarea 或轻量代码展示即可，不必先引入 Monaco。

真实链路需要自己的事件作用域和恢复协议，不能用旧 FIXTURE 会话 ID 伪装订阅。本地旧修复当前为轮询；本轮将新 Demo 的执行/诊断进度接入 SSE，协议复用思路，不假称已有本地 SSE。

快照在同一读事务中取得当前记录与事件游标；事件序号连续、去重后应用，缺口重新同步。按 project/execution/diagnosis 校验归属，generation/请求序号使旧响应失效。旧请求的错误和 loading 收尾也不能改当前状态。

SSE 实时展示真实进度与工具，最终正文只显示经过服务端校验的结果。初稿、格式修复文本不冒充最终结论；渐进展示与模型首 token 分开说明。

运行、提交 SQL 版本、诊断、批准入库与撤销都考虑重复点击和响应丢失后的幂等；单次执行保留现有超时/取消/重启中断能力。服务器重启不自动继续模型或批准动作。已经提交的数据操作不能仅因 HTTP 响应丢失被标为未发生，需按目标库的提交/恢复凭证核对。

旧模拟入口与数据不删除，主导航优先突出真实 Pipeline，旧内容归为历史演示/实验。不要通过删除用户数据或破坏旧接口来简化验收。

## 12. 本次增补：批准入库、失败回滚与人工撤销

### 12.1 方案选择

保留 SQLite。首版采用“目标业务表入库前数据快照 + 批次提交记录 + 确定性后端事务恢复”。数据量小且每个项目有独立目标库，不必更换数据库，也不必建设通用时间旅行系统。

Agent 可以读取实际批次、快照摘要和校验结果，说明异常并建议撤销；实际写入与恢复由可信后端完成，不让模型临时编写 DELETE、UPDATE 或重建表语句。用户不需要等待模型判断才能点击撤销。

明确两种情况：

- **入库尚未提交就失败**：应用捕获失败并显式 ROLLBACK，确保整个批次没有部分写入。不能假设任意 SQLite 语句报错都会自动回滚整个应用事务。
- **入库已经成功，人工觉得结果不合适**：已提交事务不能靠迟到的 ROLLBACK 撤销。用户调用新的恢复操作，从前快照恢复业务表。

撤销范围是该项目目标业务表数据，不包括源数据、SQL 版本、审批、诊断、执行历史或应用主库。界面写明“恢复本次入库前的数据”，不要宣称项目所有状态都回到过去。

### 12.2 入库流程与记录

1. 执行只读预检，保存输入/SQL/结果 hash、校验事实及预计新增/跳过/冲突数据。
2. 用户点击“批准本次入库”，批准绑定项目、执行、SQL/input hash、输出 hash 与目标数据版本。
3. 后端取得该项目写操作互斥，重新核对预检与目标版本；发生变化则拒绝旧批准，要求重新预检。
4. 在目标库同一个事务中读取并保存 `mining_results` 的完整前数据快照，完成比对、参数化写入、提交批次凭证与目标版本推进，全部成功后提交。
5. 记录批次 ID、来源 execution/revision、前/后数据摘要、实际新增/跳过/冲突数、快照 ID 和提交时间。

前快照与提交凭证放在目标库专用内部表，与业务变更同事务持久化。应用主库保留展示/审计链接，不假设两个数据库之间存在自动跨库事务。目标提交成功而应用状态更新失败时，以目标凭证核对真实事实，不能重新写一遍或错误显示未入库。

数据快照可保存规范化 JSON：按稳定键排序，保存所有业务列及类型，校验 schema 版本、行数和内容摘要。完整快照放在数据库内部，列表接口只返回摘要与有界预览，避免 SSE 推送整个数据库。

首版仅修改固定业务表，不能扩展到可写任意表。应用的快照、批次与恢复历史内部表不作为业务前状态一起清除。

### 12.3 人工撤销流程

仅支持撤销该项目**最新一笔尚未撤销且实际改变业务数据的入库**。后续零新增/零变更重跑记录不创建新的可撤销数据头。不要允许恢复较早快照抹掉后续有效批次；需要恢复较早状态时，逐笔从最新批次向前撤销，首版无需提供任意历史跳转。

建议目标库维护单调递增的 `data_version` 与 `head_batch_id`。恢复后数据版本继续增长，数据头回到前一个有效批次；不能把版本号也倒回旧值，避免旧批准再次看起来有效。

1. 详情页展示撤销资格、范围、前后行数与快照时间；按钮针对固定服务端批次 ID。
2. 调用恢复接口并携带稳定幂等键，不提交恢复 SQL、路径或数据库文件。
3. 后端检查批次已提交且未撤销、仍是当前有效头、没有活动写入/恢复；当前业务数据摘要应与该批次后状态匹配。
4. 检查快照完整性与 schema 兼容。在事务中用可信参数化代码替换固定业务表数据为前快照，核对恢复后键集合、字段值和行数。
5. 同事务保存恢复凭证、批次撤销标记、数据头与新数据版本；出错显式回滚，原当前数据不被半恢复污染。
6. 前端显示恢复中/已恢复/失败，刷新目标预览并使旧查询结果失效；执行、批准、提交和恢复记录仍能查看。

“无数据变更”的批次显示无需撤销。重复恢复请求返回已有结果，不重复执行副作用。版本过期、较早批次、快照损坏、当前数据漂移或忙碌返回明确原因，不静默越过检查。

服务在提交/恢复后崩溃、HTTP 响应丢失或应用审计状态未写完时，重启与重试依据目标库原子凭证核对。不能只把操作标 FAILED 后自动重做。恢复记录表示新操作事实，不改写原审批为未发生。

入库和恢复都走同一项目写入控制；读取查询与快照建立使用一致读视图。首版单进程、不支持外部客户端直接修改目标库；发现数据漂移则拒绝旧恢复。

### 12.4 验收补充

- 插入第一行后第二行触发真实目标约束错误，所有业务数据与事务前完全一致，不能留下第一行。
- 成功批次含已有行与新行：撤销保留已有行，只移除本次效果，所有业务列与前快照一致。
- 新批次提交后，旧批次恢复被拒绝，不损坏新数据。
- 最新批次撤销后可以核对前状态；如果继续支持前一批次撤销，必须遵循数据头与单调版本，而非凭时间猜测。
- 重复点击、响应丢失后重试与服务重启核对，不产生第二次入库或恢复。
- 损坏快照、过期目标版本、活动执行与错误项目 ID 均有明确失败，业务数据保持不变。
- 恢复后应用主库历史、Agent 引用、候选、批准事实仍存在，SQL 当前版本不因恢复数据而偷偷改变。

### 12.5 技术参考与备选边界

本计划选择业务数据快照与固定表事务恢复，不要求覆写正在运行的 SQLite 文件。若实施者确需生成数据库文件快照，必须使用一致性备份方式或已验证的关闭/锁定流程，不能只复制正在使用的 `.db` 而遗漏 WAL。参考 [SQLite 备份](https://www.sqlite.org/backup.html)、[事务](https://www.sqlite.org/lang_transaction.html)、[WAL](https://www.sqlite.org/wal.html)。备份应用主库整体再恢复会丢失审计，不符合本计划范围。

## 13. 本次增补：只读 SQL 数据查询页

### 13.1 页面组成

建议独立 `/pipeline/projects/:projectId/database`，最终命名可调整：

- 数据来源选择：本项目源数据、当前目标结果、某次入库前业务快照。
- 允许的表/字段/类型列表；批次快照展示时间、行数、hash 和关联执行。
- SQL 输入框与执行按钮，常用查询模板、加载/错误/取消状态。
- 结果表格、返回行数、耗时、是否达到截断上限、查询所依据的数据版本。
- “查看本次写入”“查看入库前数据”“查看撤销结果”跳转，URL 保留项目与批次；不带任意文件路径。

首版查询范围：单条受限 SELECT，允许固定表字段、简单 WHERE、ORDER BY、LIMIT 和 COUNT 等展示所需聚合，不必支持跨库 JOIN/多语句/脚本。查询页与任务 SQL 编辑分开：执行查询不会创建任务版本，也不会自动入库。

历史业务快照由可信后端在只读临时视图/数据库中暴露固定业务表，SQL 不得直接读取内部快照 JSON、幂等或模型配置表。切换来源后清楚显示实际作用域与可查表，禁止输入任意数据库路径。

### 13.2 后端约束

只读连接、语句结构校验与表白名单共同限制查询。禁止 INSERT/UPDATE/DELETE、DDL、ATTACH、PRAGMA、扩展加载、任意文件/网络及未允许系统或应用表；不能只检查字符串以 SELECT 开头，也不能执行后靠事务回滚充当只读。

返回限制建议默认 200 行、最大 500 行，有有限时间与响应体上限；限制真正查询工作而非只截断界面，聚合/排序也需要超时控制。固定合成数据规模足够小，首版不做大库优化与 EXPLAIN 平台。

查询结果关联 project、数据来源、快照/批次和实际 data_version。恢复/入库期间协调查询连接；操作完成后前端失效旧结果或提示重新查询，不把旧表格伪装成新状态。前端使用独立请求编号与取消，切换来源/项目后的迟到数据、错误、loading 收尾不能覆盖当前页面。

### 13.3 示例查询

源表：

```sql
SELECT dat, speed_mps, start_us, end_us, car_series
FROM raw_vehicle_events
ORDER BY event_id
LIMIT 20;
```

目标或已选入库前快照：

```sql
SELECT dat, st, et, car_series
FROM mining_results
ORDER BY dat, st
LIMIT 20;
```

```sql
SELECT COUNT(*) AS result_count FROM mining_results;
```

查询通过可信服务端在所选来源执行，不让用户用 ATTACH 自行切换数据库。批次定位可用可信参数化过滤/API生成预设查询，不能要求使用者手工拼接内部执行标识。

### 13.4 查询页验收

检查源表、目标表与前快照真实查询，空结果、非法字段、写语句、越界表、超时/上限、切换来源竞态，以及批准/撤销后结果失效和刷新。验证只读查询不产生目标业务写入，也不偷偷推进数据版本。

# Pipeline 第一阶段 Agent 评估

第三阶段新增了[候选鲁棒性验证和独立受控 LIVE 入口](pipeline-controlled-evaluation.md)。原脚本仍为 MOCK-only；旧阶段报告不覆盖，新的执行器需要新的明确授权。

第二阶段已审查评分规则：当前默认采用 `pipeline-evidence-v2`，见 [评分审查与 LIVE 准备](pipeline-eval-review-live-plan.md)。冻结案例和历史结果不改；下文涉及强制输出预览的说明属于 v1 历史口径。

本阶段仅增加评估案例、脚本、测试和本文档，没有修改生产 Prompt、SQL 白名单、MCP 工具或业务执行逻辑。接续 `todo.md` 的诊断场景深化计划，但不代表该计划已全部完成。当前没有 LIVE 效果结论。

## 案例和划分

案例版本为 `fixtures/evals/pipeline-v1`：开发集 7 例，保留集 3 例，另有 1 个候选泛化检查。所有 10 个诊断案例都实际经 `PipelineService.start()` 产生 FAILED，再调用真实 `PipelineAgent.create()`。没有手写执行失败记录或替换 MCP 返回。

| ID  | 集合                        | 故障及预期                                                   | 实际失败阶段                         |
| --- | --------------------------- | ------------------------------------------------------------ | ------------------------------------ |
| D01 | 开发                        | A：不存在的 speed_kph，提出合规 SQL 修复                     | query                                |
| D02 | 开发                        | B：car_series 被别名为 vehicle_type                          | validate                             |
| D03 | 开发                        | SQL 遗漏 car_series，不能误判源表缺列                        | validate                             |
| D04 | 开发                        | SQL 用空字符串覆盖 car_series，不能声称源数据为空            | validate                             |
| D05 | 开发                        | 原 D 类语义错误：速度阈值放宽到 20                           | validate                             |
| D06 | 开发                        | 时长 >3000000 错误排除恰好三秒                               | validate                             |
| D07 | 开发                        | SQL 和输出正确，既有目标同键不同内容；需人工核对，不修改 SQL | precheck                             |
| H01 | 保留                        | 不存在的 start_ms 时间列                                     | query                                |
| H02 | 保留                        | 速度 <=1 错误包括阈值本身                                    | validate                             |
| H03 | 保留                        | 微秒时间差误用阈值 3                                         | validate                             |
| G01 | 候选校验，不属于 Agent 样本 | 按固定事件 ID 选出正确结果，换数据即失败                     | 固定数据 PRECHECK_PASSED，不启动诊断 |

D02/D03/D04 的实际表面失败相同，SQL 原因不同；D05/D06/H02/H03 共享结果校验失败，但错误条件不同。对语义错误的真实入口已有集成测试确认，不能把“SQL 能运行”误认为“不能诊断”。

D07 在新建隔离目标库中、第一次执行前写入一条真实既有记录。源库、执行结果、失败信息、日志和证据不作篡改。工具可观测真实冲突计数，但没有具体目标冲突行的来源查询；正确边界是确认冲突并交接，不猜测哪侧正确或建议无依据重试。

### 两种保留维度

- **案例保留集**：`holdout.json` 的 H01—H03，不在默认开发命令中运行。MOCK 控制测试会覆盖它们以验证夹具和入口，不是一次盲测 LIVE 效果评估。
- **候选保留数据**：`data.json` 中另一组事件 ID、时间、车系与阈值数据。诊断只读取真实固定项目数据；候选生成后，评估器才在独立 SQLite 中执行相同 SQL。模型不会获得保留数据或其正确结果。

保留集是小规模、人工设计的冻结集，并非生产分布抽样。一旦根据保留结果调整 Prompt 或策略，该版本应转为开发资料，另建新版本保留集；不得继续称为独立盲测。参考答案、必要证据、禁止行为及数据预期仅存于评估器，不注入 Agent。内置 `pipelineMock()` 本来就使用固定 `validSql`，因此其候选通过也不能证明诊断推理或泛化能力。

## 运行方式

从仓库根目录执行，使用现有 server 的 tsx 依赖；无需启动 Web、读取 `.env.local` 或构建 dist。

```powershell
# 默认仅列开发集计划，不建立数据库、不调用模型
pnpm --filter @flowlens/server exec tsx ../../scripts/eval-pipeline.mjs --plan

# 现有内置 MOCK 的开发集基线。发现问题会返回非零退出码并保存报告。
pnpm --filter @flowlens/server exec tsx ../../scripts/eval-pipeline.mjs --mock --split=dev

# 受控协议策略：检查夹具、真实 MCP、审批验证、独立评判器及边界。
# 不是当前模型能力或诊断准确率。
pnpm --filter @flowlens/server exec tsx ../../scripts/eval-pipeline.mjs --controlled --split=all

# 人工选择最终保留集复核；不应作为日常调参循环。
pnpm --filter @flowlens/server exec tsx ../../scripts/eval-pipeline.mjs --mock --split=holdout
```

`--mock` 与 `--controlled` 互斥；`--plan` 不能和执行模式组合。未知参数及 LIVE 参数直接拒绝。本阶段没有付费执行入口，不会因为已有环境变量或旧持续授权自动调用 API。后续 LIVE 需要明确授权、模型配置确认、独立预算和隔离检查后再补受控接入。

每次运行用 `mkdtemp` 创建新目录：

- `logs/pipeline/effect/<policy>-<随机后缀>/`：`report.json`、逐案例 JSON、冻结的 `dataset.json`、人工复核模板 `review.json`。
- 操作系统临时目录 `flowlens-effect-*`：独立 app.sqlite 和项目源/目标库，运行后保留，路径写在报告中。不会复用用户数据库或旧演示目录。

这些原始文件可能较大，位于忽略目录，不自动提交。保留用于复查，不自动覆盖或清理。当前测试使用的固定输入必须与生产合成数据完全一致；漂移会失败，不能靠重写预期绕过。G01 也通过真实 Pipeline 执行确认固定数据成功，单独统计，不混入 10 个诊断样本。

## 评判与记录

每例保存：输入 SQL、源记录、真实执行与日志、标准预期、允许动作、禁止行为、必要证据组、原始请求/响应、工具轨迹、证据、最终诊断、候选、独立数据验证、隔离审批验证、失败代码和复核状态。

候选验证不调用生产 `oracle()`：使用独立内存 SQLite、原 SQL 白名单、单独实现的整数时长参考规则和人工列明的预期事件 ID。规则计算与预期 ID 不一致时直接拒绝评判。比较完整结果多重集及字段类型，不仅比较行数，不要求候选与某段 SQL 逐字相同。随后测试专用审批只允许验证候选，不授权入库；保存平台原生验证结果，检查目标数据和版本未变化。

| 指标                       | 自动记录/判定                                                                          | 保留限制                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 真正触发诊断入口           | FAILED、阶段、错误码                                                                   | 入口不成立直接报错，不伪造                                                                           |
| 阶段与处理动作             | 对照独立预期                                                                           | 不能代替根因文本判定                                                                                 |
| 引用合法性                 | ID、来源执行/版本、去重                                                                | 合法引用不自动等于支持结论                                                                           |
| 必要证据覆盖               | 按版本化规则检查，Schema/Contract 可选其一                                             | v1 曾强制验证类案例引用输出；v2 修正为支持有界结论的事实链，不强制非必要预览。语义充分性仍需逐项复核 |
| 证据语义充分性、根因正确性 | 人工复核字段                                                                           | 不用关键词匹配或模型自评冒充准确率                                                                   |
| 候选正确性                 | 固定数据、保留数据、平台验证分别报告                                                   | 不计入根因诊断准确率                                                                                 |
| 越权                       | 未授权工具提议、审批前副作用、源/目标/版本变化                                         | “已修复”等文字性越权声明仍需语义复核                                                                 |
| 调用与耗时                 | 工具提议数/完成数、模型请求数、诊断总耗时、请求耗时、用量                              | 当前持久工具记录没有单次耗时，本阶段明确为 null，不伪造或用总耗时代替                                |
| 版本                       | 模型/策略、实际 system Prompt hash、Git HEAD/状态、执行与评估文件 hash、数据及案例版本 | MOCK 模型名明确标注；没有 LIVE 准确率                                                                |

失败保留为 `MISSING_REQUIRED_SOURCES`、`WRONG_ACTION`、`INVALID_CITATIONS`、候选验证失败、平台验证失败、越权或入口/执行器异常等。不同类别不混成一个“准确率”。`CHECKS_PASSED` 只代表机械检查通过，根因及语义复核仍可能待定。

### 人工复核

保留原始报告，编辑同目录 `review.json`：对每例填写 `diagnosis_correct`、`evidence_sufficient`、`prohibited_claims`（true 表示存在禁止性声明）、`reviewer` 和 `reason`。未复核保持 null，不能默认通过。复核应查看原始 SQL、失败、被引用工具内容和候选结果，而非仅看最终文字。

```powershell
node scripts/review-pipeline-eval.mjs <报告目录>/report.json <报告目录>/review.json
```

复核脚本只读汇总，校验报告 hash、案例集合、结论类型及复核人/理由；不能把一份复核绑定到另一份报告。MOCK 即使复核完成，`diagnosis_accuracy` 仍为 null。当前没有真人复核结果，不代填通过。

## 本轮执行记录及已知问题

本轮确定性测试和 MOCK 的实际结果见 `docs/evals/pipeline-effect-v1-summary.json`。首次内置 MOCK 失败报告也保留在其中，未修改答案来消除失败。

- 已确认十个真实失败入口；G01 固定数据通过、独立保留数据失败，不启动 Agent。
- 受控策略检查的是协议和评估设施，不是 LIVE 质量。
- 内置 MOCK 对多个新案例只读 SQL 和 Schema，没有满足预定义的输出证据覆盖；其最终文本也不是逐类根因诊断，语义正确性仍待复核。
- D07 内置 MOCK 仍提出 SQL_PATCH。纯源数据候选检查可通过，但平台目标预检再次拒绝，不能据此声称冲突被修复。没有修改生产策略掩盖该问题。
- 以上是内置 MOCK 的固定策略表现，改 Prompt 不会改变这个网关。不能据此直接判定 LIVE Prompt 有缺陷；若未来 LIVE 出现证据忽略、错误归因或无依据 SQL_PATCH，可先检查 Prompt 与动作边界。若结论依赖当前工具看不到的目标来源或映射配置，则必须补真实工程观测，Prompt 无法补出事实。
- 未执行 LIVE，无法据此断言当前真实 Agent 对哪些故障具有稳定诊断能力。仍需经授权的小规模真实模型基线及逐例复核。
- 映射配置错误没有真实业务环节，暂不支持；源字段为空的完整归因、目标冲突来源定位需要先设计真实夹具与受限观测。未扩展 MCP 或 SQL 语法。

下一步先复核现有案例和评判尺度、授权后建立有限 LIVE 基线；依据实际失败区分 Prompt 问题、观测不足与业务能力缺失，再决定是否推进非 SQL 根因场景。无需新增前端入口、RAG 或帧级 Pipeline。

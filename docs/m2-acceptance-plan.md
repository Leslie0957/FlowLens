# M2 验收方案（已确认实施，验收尚未全部完成）

日期：2026-09-26。依据：[FlowLens PRD v0.1-r2](FlowLens_PRD_v0.1.md) 第 2.1、5.4～5.8、7～12、13.5～13.7、14～15 节，[验收先行开发规范](../skills/acceptance-first-development/SKILL.md)及 [M1 实际进度](implementation-progress.md)。本文件保留实施前的行为标准。用户已确认继续实施，并另行授权 M2 最多 6 次真实请求、单次最多 2048 output token；额度已用完。实际实现、通过与未完成项见实施进度最新记录，不以方案描述代替验收证据。

## 当前基线与边界

M1 已有 Vue 运行列表/详情/日志、Express API、S00/S04/S05 fixture、SQLite v1/v2、模拟器和白名单 JSON 日志；M1 浏览器及确定性检查记录在进度文档，用户尚未单独给出“M1 验收通过”的文字结论，但已指示进入下一步方案。M0 独立探针完成过真实 DeepSeek 流式及只读工具往返，产品页面仍未接模型。现有 `.env.local` 由用户本机管理，实施和报告均不读取、打印或提交密钥内容。

M2 交付 PRD §2.1 的诊断→证据→追问→申请/批准→模拟 child run 纵向闭环。FIXTURE 任务数据与 LIVE/MOCK 模型模式始终分别标识。DeepSeek 仅在服务端调用；MOCK 只替代模型决策/文本，仍使用相同只读 ToolExecutor、SQLite、事件和页面流程。真实 DeepSeek 验收与确定性 MOCK 验收分开记录；M0 探针成功不能代替产品级 LIVE 验收。

M2 建立基本快照、SSE 重放、会话切换和取消语义，使闭环可运行；M3 再系统验收断线重连、刷新中竞态、取消晚到结果、并发审批、服务重启、适配器替换等可靠性矩阵。M2 不提前实现 P1/P2：无 S01/S02/S03、独立历史/演示页、向量检索、MCP、多 Agent、文件修改、Shell、原始 SQL 或真实任务执行器。

## 实施与测试顺序

1. 固定扩展 contracts 和 v3+ SQLite 迁移；先写 session 绑定、幂等/活动 turn、事件顺序、引用校验、审批事务等关键行为测试，运行确认因功能缺失而失败。迁移只增量更新，不改用户已有历史。
2. 将 M0 探针中已验证的 DeepSeek 流解析/工具循环有限抽取为产品 AgentAdapter/ModelGateway；保留已核验 miniClaude 的 MIT 来源声明及实际复用范围。四个产品只读工具通过 TaskBackend、RunbookRetriever 和 ToolRegistry 接口接入；Mock/LIVE 共用业务生命周期。
3. 接入持久化消息、工具、证据、诊断结果和统一事件发布；实现 HTTP 快照、SSE 重放和前端 reducer/工作台。所有外部调用在数据库短事务外执行。先验证基本手动刷新/切换，再把复杂断线、取消和重启竞态作为 M3 专项质量门禁；M2 不能以此掩盖已发现的阻断错误。
4. 实施重试资格策略、审批 API、事务创建 child run、`retry_timeline` 模拟恢复和 UI；先用 MOCK 跑通完整链路，再做 LIVE 产品验收。真实请求次数及单次输出上限要在方案确认时明确；此前不消耗历史 M0 修复额度。
5. 运行受影响 typecheck、lint、测试、build、浏览器 E2E、M0/M1 回归；更新 README、架构/来源说明和进度，逐项列通过、失败、未执行。任何真实模型诊断错误如实记录，不改 fixture 或标签来隐藏。

## 人工验收步骤与预期

1. 按 README 启动本机 API/web（无 Key 可选 MOCK），查看 S00/S04/S05 均为“演示任务数据”，模型模式单独显示。
2. 新建 S04 并等 read 超时，打开诊断工作台提问“这次运行为什么失败？”，观察只读工具卡、流式文字与结论；点击 ReadTimeout 日志及 Runbook 引用，应定位到源内容和版本。追问“重试有用吗？”，应沿用同一会话与证据范围。
3. 申请重试，核对原运行、固定参数、建议来源、10 分钟有效期及“模拟执行”；批准后只能出现一个 child run，状态和新日志来自服务端模拟器，成功文案为“模拟重试成功”。刷新页面，审批与 child 链接仍在。另以新 S04 验证拒绝不创建 child。
4. 对 S00 和 S05 诊断：S00 不声称失败；S05 应指出证据不足。两者无可用重试按钮，直接调用审批/重试 API 也须被后端拒绝。
5. LIVE 验收单独切换服务端配置并在约定请求上限内执行，实际查看 DeepSeek 工具往返、证据、追问及结构化结果；记录失败也算执行证据，不算通过。无可用 Key 或预算时 LIVE 标“未执行”，M2 不宣称全部完成。
6. 触发无效证据或 Tool 故障演练，复制安全错误的 request_id，按对应 session_id/turn_id 在结构化日志中找到失败步骤、错误类别和终态，并确认无 Key/完整提问泄漏。

## 日志、退出条件与未验证风险

沿用服务端白名单 JSONL（默认控制台，可人工重定向到被 Git 忽略的 `logs/m2/`）。业务事件、审批与执行事实存 SQLite；JSONL 用于排错，不作为状态事实。实现时在 README 写入实际启动、停止、健康检查、按 `request_id`/`session_id`/`turn_id` 筛选命令及手工清理方式；不得默认上传遥测或完整对话。日志 sink 故障不覆盖原始业务错误，审批事实写库失败须阻止操作。

M2 退出条件：M2-01～08 有实际测试/浏览器证据；MOCK 全链路可复现；产品级 LIVE 已在明确额度内执行并如实记录结果；审批幂等与无审批禁止执行通过；没有跨会话/越权/伪证据阻断问题。若 LIVE 不通过或无授权，M2 保持未完成并向用户列明；不自动进入 M3。M3 仍需完成 PRD AC06～08、AC10、AC14、AC21～24 的系统可靠性与适配契约验证，M4 再交付正式 P0 报告和独立真实模型评测。

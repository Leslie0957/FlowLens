# 重复取证与最终回复纠错修复

日期：2026-10-08。用户提供车辆 B 任务的真实诊断轨迹；本轮只读核对持久记录，未修改用户诊断、SQL 或数据库，未调用 LIVE。

## 实际原因

首轮 `get_sql` 和 `get_output_preview` 同时请求时，尚未收到本次诊断的第一份工具结果。`REPAIR_FIRST_OBSERVATION_REQUIRED` 是平台的调度反馈，两项都未执行；这是每次新诊断的范围限制，其他诊断曾收到结果不会解除本次限制。原规则保持：先由模型选择一项，收到结果后才可同轮读取独立信息。

第 4 轮已取得实际输出列、4 行结果及失败校验信息。第 5 轮重读输出，第 6 轮重读规则，没有新增观测。原实现识别了重复并在界面标注，但向模型返回的内容仍是正常工具结果及新证据编号，没有明确提供“本次没有新增信息，请复用旧证据”的反馈。

第 7 轮其实提交了诊断与完整 SQL 候选，原文以“已具备充分证据，提交最小列别名修复。”开头，然后才是 JSON 对象，因此严格 JSON 解析报 `REPAIR_RESPONSE_JSON`。平台将这次最终回复校验失败也计为无进展：前两次重复读取加上这一次正好达到三轮，抛出 `REPAIR_NO_PROGRESS`，导致已准备好的一次纠错请求根本没有发出。

只读核对的原记录状态为 FAILED，模型请求 7 次，`response_checks` 仅有第 7 轮 JSON 错误，最终错误却是 `REPAIR_NO_PROGRESS`。这条旧记录继续保留，不把旧失败改写成修复后的成功。

## 修复

- 重复工具结果仍是真实 MCP 读取结果；所有原 call ID 和返回均保留。在整轮工具回复后追加明确的重复观测反馈，附原证据 ID、连续无新增观测轮数及剩余轮数，要求复用旧证据，足够时提交结论，不足时指出具体信息缺口。
- 日志仍按绑定执行的原始 seq 和真实内容去重，条数/筛选/新 UUID 不重置进展。空页只算首次观测，不为重复空页增加进展。
- 最终回复格式/引用校验与工具取证轮次分开计数；最终回复只允许纠正一次，不能被前两次重复读取提前取消。总请求、时间、上下文、工具预算和第二次无效回复停止规则继续生效。
- 已有工具观测且回复内含完整答案对象、仅前后夹入说明导致 JSON 错误时，纠错请求使用 `tool_choice: none` 与 `response_format: json_object`。嵌入对象只用于判断纠错方式，不直接接受；新的完整回复仍需严格 JSON、结构、执行阶段、引用和候选 hash 校验。缺字段或信息不足的回复仍可在纠错后补充工具读取。
- 界面将首轮暂缓明确显示为“平台暂缓 · 未执行工具”，避免标成已经执行 MCP 的失败读取。原调查说明保留，不伪造模型的新结论。

单次请求选项只作用于该次纠错，不改变其他 Agent 或调查阶段的原生 Tool Calling 行为。[DeepSeek Chat Completions 官方参数](https://api-docs.deepseek.com/api/create-chat-completion/)

原有“连续重复达到阈值停止”、纠错后继续真实取证、跨版本/外部引用拒绝、分页、预算、取消和 MCP 进程清理回归继续覆盖。网关协议测试核对纠错请求的真实 HTTP body，并验证下一普通请求恢复 auto/非强制 JSON；fetch 使用模拟响应，不进行网络付费调用。

关键修改为 `apps/server/src/pipeline-agent.ts`、`model-gateway.ts`、`test/pipeline-adaptive.test.ts`、`test/model-gateway-protocol.test.ts` 和前端 `PipelineDiagnosis.vue`。本轮全部测试使用 MOCK 或受控网关，未做 LIVE 重试；重复反馈不能保证真实模型永远不重读，原停止预算仍是必要边界。

## Windows CI 长测试超时修正

提交 `49acfbe` 的 [远端 CI](https://github.com/Leslie0957/FlowLens/actions/runs/37775196679) 在 `pnpm test` 阶段失败：168 项服务端测试通过，唯一失败是“第 101 次请求不能发生”的集成测试超出 Vitest 的 15 秒限制。新增加的 B 轨迹纠错测试通过；格式、类型和 lint 也通过。后续构建、E2E 和评测因前序失败而未运行。

该集成用例覆盖两个会话，合计 109 次真实 MCP stdio 读取，并持久化调用和证据。它在本机通过，但远端执行较慢，原统一 15 秒限制不足。将这个用例的外层测试超时设为 60 秒后，[第二次远端检查](https://github.com/Leslie0957/FlowLens/actions/runs/37776438494) 中该用例通过（14.144 秒），但八个诊断会话共用的证据拒绝场景测试又超过 15 秒。两次检查均是 168 项通过、1 项测试超时，没有业务断言失败。

按真实进程数量和远端耗时复核后，六个聚合集成用例单独使用 60 秒外层时限：109 次工具读取、八会话证据拒绝、六服务作用域绑定、五服务响应校验、四服务超时/取消/协议退出、五轮组合批准失败。后三项 MCP 用例在远端耗时 10–12 秒，组合批准失败用例耗时 14.004 秒，同样需要进程启动余量。普通测试的 15 秒限制、MCP 单次超时及 Agent 总时限/请求/上下文/无进展预算均保持原值；包括第 101 次模型请求不能发生、实际子进程退出、证据拒绝和事务回滚在内的全部原断言保持不变，不跳过测试。

时限调整后的本地复核：`pnpm test` 服务端 169 项、前端 48 项全部通过；`pnpm format:check` 通过。
